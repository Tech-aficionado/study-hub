🔬 Pull Requests In Depth Intermediate

Drafts, linked issues, review requests, suggested changes and resolving conversations — the full PR toolkit.

1 Draft pull requests

Open a PR as a Draft when the work is in progress. Drafts run CI and are visible to the team, but cannot be merged and do not send review-request notifications until you click "Ready for review". Use them to get early CI feedback or show direction without consuming a reviewer's time.

gh pr create --draft --title "WIP: new auth flow" --body "Early look, not ready yet"
gh pr ready            # flip the current PR from draft to ready

2 Linking issues and auto-closing

In the PR description, closing keywords create a link and auto-close the issue when the PR merges to the default branch:

Closes #17
Fixes #42, fixes #43        # one keyword per issue

You can also link via the Development sidebar on the PR. Linked issues show on both sides, so anyone reading the issue sees the PR that will close it.

3 Requesting reviews

Add reviewers from the Reviewers sidebar, or let a CODEOWNERS file auto-request them. A review ends in one of three states:

StateMeaning
ApproveLooks good — safe to merge
Request changesBlocks merge until addressed (if required)
CommentFeedback without a verdict

4 Suggested changes

A reviewer can propose an exact code edit inside a comment using a suggestion block. The author then applies it with one click — no local checkout needed. This is the fastest way to fix typos and small tweaks.

# In a review comment on a specific line:
```suggestion
const timeout = 5000; // was 500
```
💡 You can batch-apply several suggestions into a single commit via "Add suggestion to batch", keeping history tidy.

5 Resolving conversations

Each review comment thread can be marked Resolved once addressed, collapsing it so the PR stays readable. Repos can require that all conversations are resolved before merge — a branch-protection option that stops a comment from being quietly ignored.

6 Keeping a PR mergeable

  • Update branch — pull the base branch's new commits into your PR branch (merge or rebase) so it is current.
  • Re-request review after pushing fixes so reviewers get re-notified.
  • Force-push carefully — rewriting a PR branch's history is fine on your own feature branch, but tell reviewers so stale comments make sense.
