🔀 Merge Strategies Intermediate

The three ways GitHub can land a PR — and exactly what each one does to main's history.

1 The starting point

Imagine a feature branch with three commits (C1 C2 C3) opened against a main that has moved on with its own commit (M2). The three strategies differ entirely in what main looks like afterwards.

2 Merge commit (--merge)

Keeps every PR commit exactly as-is and adds one extra merge commit (MC) that ties the two histories together. History is complete but non-linear — it has a visible "diamond".

Use when commit-level history matters and you want to preserve exactly how the work was done.

3 Squash and merge (--squash)

Collapses all PR commits into a single new commit (S) on main. The messy "wip", "fix typo", "oops" commits disappear; main gets one clean commit per PR. The most popular default for application repos.

💡 Squash gives you a tidy, bisect-friendly main where every commit is a complete feature. The trade-off: individual authorship/steps inside the PR are lost on main (still visible in the PR itself).

4 Rebase and merge (--rebase)

Replays each PR commit individually on top of main with no merge commit. You keep every commit and get a perfectly linear history — but the commits get new SHAs because their parent changed.

⚠️ Because SHAs change, rebase-merge rewrites "history" in the sense that the commits are copies. Fine for merging a PR; avoid rebasing commits others have already pulled.

5 Choosing — and the CLI

Want…Use
Clean one-commit-per-feature mainSquash
Full fidelity of how work happenedMerge commit
Linear history but every commit keptRebase
gh pr merge 42 --squash      # or --merge / --rebase
gh pr merge 42 --squash --delete-branch   # tidy up the feature branch

A repo's Settings can disable whichever strategies you don't want, so the team is funnelled into one consistent style.
