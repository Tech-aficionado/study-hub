1 Matrix builds — run the same job many ways

A strategy.matrix expands one job definition into many parallel jobs, one per combination. Perfect for testing across versions and operating systems.

jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci
      - run: npm test

This single job becomes 3 × 3 = 9 runs. fail-fast: false lets the others finish even if one fails; include/exclude tune specific combinations.

2 Caching dependencies

Each job starts on a clean runner, so dependencies re-download every time. actions/cache stores a folder keyed by a hash of your lockfile and restores it on the next run — turning a 90-second install into a few seconds.

- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
    restore-keys: npm-${{ runner.os }}-
💡 Many setup-* actions have built-in caching (cache: 'npm' on setup-node) — simpler than a manual cache step.

3 Artifacts — passing files between jobs

Caches speed up re-runs; artifacts move outputs (a built binary, a test report, coverage) out of one job so another job — or a human — can download them.

- uses: actions/upload-artifact@v4
  with:
    name: dist
    path: dist/

# in a later job that "needs" the first:
- uses: actions/download-artifact@v4
  with:
    name: dist
⚠️ Artifacts count against your account's storage quota. A "storage quota exceeded" error fails the upload step and can skip the steps that depend on it — delete old artifacts or set a short retention.

5 Environments with approvals

An environment (e.g. production) groups deployment config and can enforce protection rules: required reviewers who must click Approve before the job runs, a wait timer, and environment-scoped secrets.

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://myapp.com
    steps:
      - run: ./deploy.sh

When this job is reached, it pauses and waits for a named reviewer's approval — human control over automated deploys.

6 Concurrency — stop overlapping runs

Without a limit, pushing twice quickly starts two deploys that race. A concurrency group serialises or cancels runs in the same group.

concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: true   # newest push wins; cancel the older run

7 Reusable workflows & permissions

A reusable workflow (triggered by workflow_call) is a workflow other workflows invoke like a function — define your deploy once, call it from many repos. Pair it with least-privilege permissions: the automatic GITHUB_TOKEN should only get the scopes a job needs.

# caller
jobs:
  call:
    uses: my-org/.github/.github/workflows/deploy.yml@main
    with:
      target: prod
    secrets: inherit

# set default-deny then grant only what's needed
permissions:
  contents: read
  id-token: write   # required for OIDC
🛑 If any job writes with GITHUB_TOKEN (creating a release, pushing) but you never set permissions:, the token may be broader than needed. Declare an explicit minimal permissions block — our playground's YAML checker flags exactly this.

8 OIDC — deploy with no stored cloud secret

OpenID Connect lets a workflow prove its identity to a cloud provider and receive a short-lived credential at run time — so you never store a long-lived AWS/Azure/GCP key as a secret. The job requests a token (id-token: write) and exchanges it for cloud access via a trust policy you configure on the cloud side.
