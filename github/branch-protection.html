🛡️ Branch Protection, Rulesets & CODEOWNERS Advanced

Enforcing "nothing bad reaches main" with settings rather than trust.

1 Why protect a branch

By default anyone with write access can push straight to main, including force-pushes that rewrite history. Branch protection turns the important branches into something you can only change through a reviewed, tested pull request. It converts "we agreed not to push to main" into a rule the server actually enforces.

2 What a protection rule can require

  • Require a pull request before merging — no direct pushes; everything goes through a PR.
  • Require approvals — e.g. at least 1–2 approving reviews.
  • Require status checks to pass — named CI checks must be green before merge.
  • Require branches to be up to date — the PR must include the latest base commits.
  • Require conversation resolution — all review threads resolved.
  • Require signed commits, linear history, and block force-pushes / deletions.
  • Dismiss stale approvals when new commits are pushed.
💡 "Require status checks" is only meaningful once the check has run at least once — GitHub lists checks it has seen, so push a PR first, then pick which checks to require.

3 Rulesets — the modern successor

Rulesets are the newer, more powerful system that largely supersedes classic branch-protection rules. Advantages:

  • Layered — multiple rulesets can apply to the same branch and combine, instead of one rule winning.
  • Target by pattern — apply to branches and tags via fnmatch patterns like release/*.
  • Evaluate mode — run a ruleset in "report only" to see what it would block before enforcing it.
  • Org-level — define once and apply across many repos.
  • Bypass lists — explicitly name who (if anyone) may bypass, with an audit trail.

4 CODEOWNERS — automatic reviewers by path

A CODEOWNERS file maps file-path patterns to the users or teams who own them. When a PR touches a matching path, GitHub automatically requests those owners' review, and (with branch protection's "Require review from Code Owners") their approval becomes mandatory.

# .github/CODEOWNERS  (last matching pattern wins)
*                   @org/maintainers
/src/payments/      @org/finance-team
*.tf                @org/infra
/docs/              @org/docs-team
/.github/workflows/ @org/devops

Place it in the repo root, .github/, or docs/. Patterns follow gitignore-style syntax; the last matching line decides ownership.

5 A sensible default for a team repo

⚠️ Protect main from day one of a shared repo. Adding protection after a messy accident is closing the barn door too late.
