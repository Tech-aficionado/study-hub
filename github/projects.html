📊 Projects, Discussions & Wikis Intermediate

The planning, conversation and documentation surfaces that wrap around your code.

1 Projects — planning on top of issues

Projects (the current "Projects" experience, formerly "Projects beta") is a flexible planning tool that pulls in Issues and PRs and lets you view them as a board, table, or roadmap. Unlike a static Kanban board, items stay live-linked to the underlying issue, so closing the issue moves the card.

2 Custom fields and views

  • Custom fields — add Status, Priority, Iteration (sprint), Estimate, or any single-select/number/date field to items.
  • Views — save multiple layouts: a board grouped by Status, a table filtered to this sprint, a roadmap by date.
  • Built-in automation — rules like "when an issue is closed, set Status = Done" without writing code.
💡 A single project can span many repos across an organisation — ideal for a team that ships from several codebases but plans in one place.

3 Discussions — the project forum

Discussions is a forum attached to the repo for conversation that isn't a bug or task: Q&A, announcements, show-and-tell, RFC-style proposals. Q&A discussions let the author mark an answer, so good replies rise to the top.

Use Discussions (not Issues) for "how do I…?" and open-ended ideas; keep Issues for actionable, closeable work. You can convert a discussion into an issue once it becomes concrete.

4 Wikis — long-form docs

Each repo can have a Wiki: a separate, Markdown-based space for documentation that doesn't belong in the code tree — design notes, FAQs, onboarding guides. The wiki is itself a Git repo (repo.wiki.git) so you can edit it locally.

⚠️ Wiki content is not versioned alongside your code and isn't easily reviewed in PRs. For docs that must track the code (API references, READMEs), keep them in the repo under /docs instead.
