🔐 Account, 2FA & Keys Beginner

Set up your identity properly before you push a single line — the account, two-factor auth, and how your computer proves who it is.

1 Creating and setting up your account

Sign up at github.com/signup with an email, username and password. Your username becomes part of every URL you own (github.com/<username>) and is awkward to change later, so pick something professional. After signing up, fill in your public profile: a real name, a photo and a bio make your contributions look trustworthy to maintainers.

💡 One e-mail address can only be attached to one account. Use a personal address you will keep for years — not a university or work address you lose access to when you leave.

2 Two-factor authentication (2FA) is now mandatory

GitHub requires 2FA for all accounts that contribute code. 2FA means that even if someone steals your password, they still cannot log in without a second factor. Think of it as a second lock on the door that only your phone (or security key) can open.

  • Authenticator app (TOTP) — e.g. Google Authenticator, Authy, 1Password. Scans a QR code and generates a rotating 6-digit code. Recommended default.
  • Passkey / security key — a hardware key (YubiKey) or a platform passkey (Windows Hello, Touch ID, phone passkey). The strongest option, phishing-resistant.
  • SMS — supported but the weakest; use it only as a fallback.
🛑 Save your recovery codes somewhere offline the moment you enable 2FA. If you lose your phone and have no recovery codes, you can be permanently locked out of your account.

3 HTTPS vs SSH — the two ways to talk to GitHub

When you git push or git clone, your machine authenticates to GitHub one of two ways:

MethodURL looks likeAuth uses
HTTPShttps://github.com/user/repo.gitA Personal Access Token (PAT) as the password
SSHgit@github.com:user/repo.gitA key pair on your machine

Since 2021, GitHub no longer accepts your account password over HTTPS for Git operations — you must use a token or an SSH key. Both are fine; SSH avoids re-entering a token, HTTPS works through corporate firewalls more easily.

4 Setting up an SSH key

An SSH key is a pair of files: a private key that never leaves your computer, and a public key you give to GitHub. GitHub proves it is talking to you by checking a signature only the private key could have produced.

# 1. Generate a modern Ed25519 key pair
ssh-keygen -t ed25519 -C "you@example.com"

# 2. Start the agent and add the key
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# 3. Copy the PUBLIC key, then paste it at Settings > SSH and GPG keys
cat ~/.ssh/id_ed25519.pub

# 4. Test it
ssh -T git@github.com
⚠️ Never share, commit, or paste the id_ed25519 file (no .pub). That is your private key — only ever upload the .pub file.

5 Fine-grained Personal Access Tokens (PATs)

For HTTPS and the API you authenticate with a token instead of a password. GitHub now offers fine-grained PATs, which are far safer than the old "classic" tokens because you scope each one tightly:

  • Resource owner & specific repositories — grant access to only the repos a script needs, not everything you can see.
  • Per-permission scopes — e.g. "Contents: read" + "Pull requests: write" and nothing else.
  • Mandatory expiry — tokens expire (max ~1 year), so a leaked token eventually dies on its own.

Create one at Settings → Developer settings → Personal access tokens → Fine-grained tokens. When Git prompts for a password over HTTPS, paste the token.

💡 Principle of least privilege: a token for a CI script that only reads code needs read on Contents and nothing more. Short expiry + minimal scope limits the blast radius if it leaks.
