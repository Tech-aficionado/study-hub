📦 Packages & GHCR Advanced

Hosting your own package and container registry inside GitHub, tied to repo permissions.

1 What GitHub Packages is

GitHub Packages is a package-hosting service that lives next to your code and shares its permission model. Instead of a separate registry account, you publish and install packages authenticated by your GitHub identity. Supported ecosystems: npm, NuGet, RubyGems, Maven/Gradle, and container images via the GitHub Container Registry (GHCR).

2 GHCR — container images at ghcr.io

GHCR hosts Docker/OCI images at ghcr.io/OWNER/IMAGE. It is the modern replacement for the older docker.pkg.github.com registry, with better permissions, anonymous pulls for public images, and images that can be owned by a user or org independently of a single repo.

# Log in (locally) with a PAT that has read:packages / write:packages
echo $CR_PAT | docker login ghcr.io -u USERNAME --password-stdin

docker build -t ghcr.io/USERNAME/my-app:1.0 .
docker push ghcr.io/USERNAME/my-app:1.0
docker pull ghcr.io/USERNAME/my-app:1.0

3 Publishing from Actions

In a workflow, log in with the built-in GITHUB_TOKEN — no PAT needed — as long as you grant packages: write.

permissions:
  contents: read
  packages: write

steps:
  - uses: actions/checkout@v4
  - uses: docker/login-action@v3
    with:
      registry: ghcr.io
      username: ${{ github.actor }}
      password: ${{ secrets.GITHUB_TOKEN }}
  - uses: docker/build-push-action@v6
    with:
      push: true
      tags: ghcr.io/${{ github.repository }}:latest

4 Visibility and linking to a repo

  • A package can be public (anonymous pulls) or private (requires auth).
  • Link a package to its source repo so it inherits that repo's access and shows up on the repo page.
  • Public container images on GHCR can be pulled with no login at all — great for open-source tooling.

5 Retention and cleanup

Every push with a new tag creates a new version; untagged versions pile up from CI. Use the package settings or a scheduled workflow (e.g. actions/delete-package-versions) to prune old/untagged versions and control storage, which (for private packages) counts toward your plan's limits.

⚠️ Deleting a package version is permanent and can break anyone pinned to that exact tag/digest — prune untagged versions first, keep released tags.
