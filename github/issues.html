🐛 Issues, Labels & Templates Intermediate

Tracking bugs and tasks the GitHub way — labels, milestones, assignees and the templates that keep reports consistent.

1 What an issue is

An issue is a single trackable unit of work living alongside the code: a bug report, a feature request, a question, or a task. Each issue has a number (#42), a title, a Markdown body, a thread of comments, and metadata — labels, assignees, a milestone, and a linked project. Because issues live in the repo, they can reference commits and PRs directly, and vice-versa.

2 Labels — colour-coded categories

Labels classify issues so you can filter them. GitHub ships a default set and you can add your own:

LabelMeaning
bugSomething is broken
enhancementA new feature or improvement
good first issueEasy, well-scoped — welcoming to newcomers
help wantedMaintainers would welcome outside help
duplicate / wontfixTriage outcomes
💡 good first issue is special — GitHub surfaces repos with these labels to new contributors, so tagging a few genuinely easy tasks is the best way to attract first-time contributors.

3 Milestones — grouping toward a goal

A milestone is a named target (e.g. "v2.0", "Beta launch") with an optional due date. You assign issues and PRs to it, and GitHub shows a progress bar of how many are closed. Milestones answer "what is left before we can ship X?" at a glance.

4 Issue templates

Templates make everyone file reports with the information you actually need. They live in .github/ISSUE_TEMPLATE/. Modern templates use YAML "issue forms" with structured fields:

# .github/ISSUE_TEMPLATE/bug_report.yml
name: Bug report
description: Report something broken
labels: ["bug"]
body:
  - type: textarea
    id: what-happened
    attributes:
      label: What happened?
      placeholder: Describe the bug
    validations:
      required: true
  - type: input
    id: version
    attributes:
      label: Version
    validations:
      required: true

You can also add a config.yml to point people to Discussions or security reporting instead of filing certain issues.

5 Linking issues to code

  • Mention #42 anywhere to cross-link an issue.
  • Closing keywords in a PR body — Fixes #42, Closes #42, Resolves #42 — auto-close the issue when the PR merges.
  • Assign an issue to yourself before working on it so others don't duplicate the effort.
⚠️ The closing keyword only triggers on merge into the default branch, and only when written in the PR description or a commit message — a plain comment saying "fixes #42" does not auto-close.
