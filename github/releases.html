🏷️ Releases & Tags Intermediate

Marking a point in history as "a version", attaching binaries, and generating changelogs.

1 Tags vs releases

A tag is a Git concept: a permanent label on a specific commit, usually a version like v1.2.0. A release is a GitHub concept built on top of a tag: it adds release notes, downloadable asset files, and a prominent entry on the repo's Releases page. Every release points at exactly one tag; not every tag has a release.

2 Semantic versioning

Most projects tag with SemVer: MAJOR.MINOR.PATCH.

BumpWhenExample
MAJORBreaking change1.4.2 → 2.0.0
MINORNew feature, backward-compatible1.4.2 → 1.5.0
PATCHBug fix only1.4.2 → 1.4.3

Pre-releases append a suffix: v2.0.0-beta.1, v2.0.0-rc.1.

3 Creating a tag and release

# annotated tag (recommended — stores author, date, message)
git tag -a v1.2.0 -m "Release 1.2.0"
git push origin v1.2.0

# create the release from the CLI, with notes and an asset
gh release create v1.2.0 ./dist/app.zip \
  --title "v1.2.0" \
  --notes "Fixes the login bug, adds dark mode"

# let GitHub auto-generate notes from merged PRs
gh release create v1.2.0 --generate-notes

4 Auto-generated release notes

GitHub can build release notes automatically from the PRs merged since the last release, grouped by label. A .github/release.yml file configures the categories and excludes certain labels. This turns "write a changelog" into one click.

# .github/release.yml
changelog:
  categories:
    - title: 🚀 Features
      labels: [enhancement]
    - title: 🐛 Fixes
      labels: [bug]
    - title: Other
      labels: ["*"]

5 Releasing from Actions, and asset tips

  • Trigger a release workflow on a tag push: on: push: tags: ['v*'].
  • Attach build artifacts (binaries per OS, checksums) so users download without building.
  • Mark a pre-release or latest explicitly; "latest" is what the Releases page and the /releases/latest URL resolve to.
💡 Publish a checksums.txt (and ideally a signature) alongside binaries so users can verify what they downloaded.
