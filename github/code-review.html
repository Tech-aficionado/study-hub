👀 Code Review Best Practice Intermediate

Review is where quality is enforced and knowledge spreads. Here's how to do it well on both sides.

1 What review is for

Code review has three jobs, in order of importance: catch defects before they ship, share knowledge so no part of the system has only one person who understands it, and keep the codebase consistent. It is not a gate to prove the author wrong — the goal is to get good code merged quickly.

2 Writing a reviewable PR (author side)

  • Keep it small. A 50-line PR gets a careful review; a 2,000-line PR gets a rubber stamp. Split large work into stacked PRs.
  • Explain the why. The diff shows what changed; the description must say why, and how to test it.
  • Self-review first. Read your own diff on GitHub before requesting review — you will catch debug prints and stray files.
  • Make CI green before asking humans to spend time.
💡 One PR = one logical change. Mixing a refactor and a feature in one PR makes both harder to review and harder to revert.

3 Giving good feedback (reviewer side)

  • Be specific and kind. "This loop is O(n²) on the request path — can we index by id?" beats "this is slow".
  • Distinguish must-fix from nits. Prefix optional comments with "nit:" so the author knows what blocks merge.
  • Use suggestions for small fixes so the author applies them in one click.
  • Approve when it's good enough, not perfect. Don't hold a PR hostage over style preferences.

5 Tools that help

  • Files changed tab — review per-file, mark files "Viewed" to track progress on big PRs.
  • Required reviewers via branch protection + CODEOWNERS — see the next page.
  • Auto-merge — queue a PR to merge automatically once all required checks and approvals land.
  • CODEOWNERS ensures the right domain expert is always asked.
