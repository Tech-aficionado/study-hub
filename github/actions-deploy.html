🚀 Deploying with Actions Advanced

A complete, modern CI → build → deploy pipeline that ships a site to GitHub Pages on every push to main.

1 The modern Pages deploy model

GitHub Pages used to require pushing built files to a gh-pages branch. The current, recommended approach deploys straight from an Actions workflow using the official Pages actions — no extra branch, with the deploy gated by a github-pages environment you can protect.

2 Enabling Pages for Actions

In Settings → Pages → Build and deployment, set Source = GitHub Actions. That switches Pages from "serve a branch" to "accept a deploy from a workflow".

3 The full workflow

# .github/workflows/deploy-pages.yml
name: Deploy to Pages

on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: ./dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4

4 Why each piece is there

  • permissions — pages: write and id-token: write are mandatory for the deploy action; contents: read keeps everything else least-privilege.
  • Two jobs — build produces the artifact, deploy publishes it. needs: build enforces order.
  • environment: github-pages — surfaces the live URL and can require approval for public sites.
  • concurrency — stops two pushes from deploying over each other.

5 Deploying elsewhere

The same shape deploys anywhere — swap the deploy job's action: aws-actions/configure-aws-credentials (via OIDC) + an S3 sync, a Vercel/Netlify CLI, SSH to a server, or a container push to GHCR. The pattern is always: build job → artifact or image → deploy job gated by an environment.

💡 Keep the cloud credential out of secrets entirely by using OIDC (id-token: write) wherever the provider supports it.
