🔐 Config & Storage Intermediate

Keeping config and secrets OUT of your container image, and persisting data beyond a Pod's lifetime.

1 ConfigMaps — non-secret configuration

A ConfigMap stores config values (URLs, feature flags, settings) separately from your image, so the SAME image can run in dev/staging/prod with different config, injected at runtime instead of baked in at build time.

kubectl create configmap app-config --from-literal=LOG_LEVEL=debug

# Reference it in a Pod spec:
envFrom:
  - configMapRef:
      name: app-config

2 Secrets — the same idea, for sensitive data

kubectl create secret generic db-creds --from-literal=password=supersecret

# Referenced the same way as a ConfigMap. Values are only base64-ENCODED, not encrypted.
envFrom:
  - secretRef:
      name: db-creds
⚠️ Base64 is encoding, not encryption — a Secret is NOT secure by default against anyone with cluster read access. Production clusters need encryption-at-rest for etcd and tight RBAC on who can read Secrets.

3 Volumes — storage inside a Pod's lifetime

By default, anything a container writes to its own filesystem is lost as soon as that container restarts — containers are meant to be disposable. A basic Volume (such as emptyDir) lives as long as the POD does, so data survives a container crash-and-restart inside that Pod and can be shared between containers in it. Delete the Pod, though, and an emptyDir is deleted with it.

4 PersistentVolumes — storage that outlives the Pod entirely

A PersistentVolume (PV) is cluster storage (a disk, a cloud volume) that exists independently of any Pod. A PersistentVolumeClaim (PVC) is how a Pod requests some of that storage. When the Pod dies and a replacement starts, it can reclaim the SAME PVC and pick up right where the data left off — essential for databases running in Kubernetes.

# pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-storage
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 10Gi
