🔐 ConfigMaps & Secrets Intermediate

Keep configuration and credentials OUT of your image, so one image runs everywhere with different settings injected at runtime.

1 ConfigMaps — non-secret configuration

A ConfigMap stores plain config (URLs, flags, whole config files) separate from the image. The same image then runs in dev/staging/prod with different config injected at runtime rather than baked at build time.

kubectl create configmap app-config \
  --from-literal=LOG_LEVEL=debug \
  --from-literal=FEATURE_X=on

# or from a file — the filename becomes the key
kubectl create configmap nginx-conf --from-file=nginx.conf
apiVersion: v1
kind: ConfigMap
metadata: { name: app-config }
data:
  LOG_LEVEL: "debug"
  app.properties: |
    retries=3
    timeout=30s

2 Two ways to consume config: env vars vs volumes

This is the key decision, and it comes up in interviews.

As environment variablesAs a mounted volume
HowenvFrom / valueFrom.configMapKeyRefvolumes + volumeMounts — each key becomes a file
Live updates?No — env is set once at startYes — mounted files update (with a short delay)
Good forSimple scalar settingsConfig files, certs, values the app re-reads
# env — all keys as variables
envFrom:
  - configMapRef: { name: app-config }

# env — one specific key
env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef: { name: app-config, key: LOG_LEVEL }

# volume — each key becomes a file under /etc/config
volumes:
  - name: cfg
    configMap: { name: app-config }
containers:
  - name: app
    volumeMounts:
      - { name: cfg, mountPath: /etc/config, readOnly: true }
⚠️ Env-var config does NOT update when the ConfigMap changes — the Pod keeps its original values until it restarts. Mounted-volume config DOES refresh in place. If you change a ConfigMap used as env, you must roll the Deployment (e.g. kubectl rollout restart deployment/app).

3 Secrets — same shape, for sensitive data

A Secret is consumed exactly like a ConfigMap but is meant for passwords, tokens, keys, and TLS certs. Values are stored base64-encoded — which is encoding, not encryption.

kubectl create secret generic db-creds --from-literal=password='s3cr3t'
kubectl create secret tls shop-tls --cert=tls.crt --key=tls.key

# consume as env or volume, same as a ConfigMap
envFrom:
  - secretRef: { name: db-creds }

Common Secret types: Opaque (default), kubernetes.io/tls (Ingress certs), kubernetes.io/dockerconfigjson (private-registry pull creds, referenced via imagePullSecrets).

4 Making Secrets actually secret

By default a Secret is only base64 in etcd — anyone with API read access or raw etcd access can read it. Hardening steps you should know:

  • Encryption at rest — configure the API server's EncryptionConfiguration so Secrets are encrypted before being written to etcd (AES-GCM, or a cloud KMS provider). This is the single most important fix.
  • RBAC — tightly limit who/what can get/list Secrets; a service account that can list Secrets cluster-wide is a serious exposure.
  • External secret stores — Vault, cloud secret managers, or the External Secrets Operator keep the source of truth outside the cluster and sync in just-in-time.
  • Prefer volume mounts over env for secrets — env vars leak more easily (child processes, crash dumps, kubectl describe on some objects).
🚨 Never commit a Secret's raw YAML (with its base64 values) to Git — base64 is trivially reversible. Use sealed-secrets, SOPS, or an external store for anything in version control.
