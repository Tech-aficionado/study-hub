🏛️ Architecture in depth Beginner → Intermediate

A cluster is a Control Plane that decides, and Worker Nodes that run — and a request flows through them in a very specific order.

1 The two halves of a cluster

Every Kubernetes cluster is split into a Control Plane (the brain that makes decisions) and one or more Worker Nodes (the muscle that runs your containers). Small clusters sometimes run both on one machine; production clusters run the control plane on dedicated, replicated machines so the cluster keeps working even if a node dies.

2 Control Plane components — the brain

  • kube-apiserver — the single front door. kubectl, controllers, kubelets and every other component talk to the cluster ONLY through the API server's REST API. It validates requests, runs admission control, and is the only component that reads/writes etcd.
  • etcd — a consistent, distributed key-value store holding the entire cluster state (every object and its desired/observed state). It is the single source of truth. Lose etcd without a backup and you lose the cluster's memory.
  • kube-scheduler — watches for Pods with no node assigned and picks the best node for each, based on resource requests, affinity rules, taints/tolerations and spreading constraints. It only sets spec.nodeName; it does not start the container.
  • kube-controller-manager — runs the background control loops (Deployment, ReplicaSet, Node, Job, EndpointSlice controllers and more) that continuously reconcile actual state toward desired state — the self-healing logic.
  • cloud-controller-manager — on cloud providers, the glue that creates load balancers, attaches disks and manages node lifecycle through the cloud's API.
💡 "Everything goes through the API server" is the single most useful mental model in Kubernetes. No component ever talks to etcd directly except the API server — that is why RBAC on the API server is the whole security boundary.

3 Worker Node components — where your app runs

  • kubelet — the agent on every node. It watches the API server for Pods assigned to its node, tells the container runtime to pull images and start containers, runs the probes, and reports Pod/node status back.
  • Container runtime — the engine that actually pulls images and runs containers, via the Container Runtime Interface (CRI). containerd and CRI-O are the common ones; Docker's built-in runtime (dockershim) was removed in v1.24.
  • kube-proxy — programs the node's networking (iptables/IPVS, or is replaced by a CNI's own dataplane) so traffic to a Service's virtual IP is spread across its backing Pods.

4 What actually happens on kubectl apply

This is the request path to burn into memory. When you apply a Deployment, no single component does everything — each watches the API server and reacts to the object the previous one created.

  1. kubectl sends the manifest to the API server over HTTPS.
  2. The API server authenticates you, runs authorization (RBAC) and admission controllers, validates the object, and writes it to etcd. At this point the Deployment "exists" but nothing is running yet.
  3. The Deployment controller (in the controller-manager) sees the new Deployment and creates a ReplicaSet.
  4. The ReplicaSet controller sees it needs N Pods and creates N Pod objects — still unscheduled.
  5. The scheduler sees Pods with empty nodeName, scores the nodes, and binds each Pod to a node.
  6. The kubelet on that node notices a Pod assigned to it, tells the container runtime to pull the image and start the containers, then reports status back to the API server (which stores it in etcd).
💡 Watch it live: kubectl get events --watch in one terminal while you kubectl apply in another shows this exact chain — ScalingReplicaSet, Scheduled, Pulling, Started.

5 The reconciliation loop — the heart of Kubernetes

Every controller runs the same loop forever: observe the current state, compare it to the desired state in the spec, and act to close the gap. You declare the end state; controllers make reality match it, continuously. Delete a Pod a Deployment owns and the ReplicaSet controller immediately creates a replacement — not because of an event handler, but because its loop noticed "4 running, 5 wanted".

⚠️ This is why editing a Deployment-owned Pod directly rarely sticks: the controller treats your change as drift from the Pod template and reconciles it away. Change the Deployment, not the Pod.
