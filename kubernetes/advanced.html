🎛️ Helm, RBAC & Scaling Advanced

Templating your YAML, locking down who can do what, and scaling automatically with load.

1 Namespaces — virtual clusters inside a cluster

A Namespace partitions one physical cluster into isolated virtual sections — e.g. dev, staging, prod — each with its own set of resources, names that don't collide across namespaces, and separate RBAC rules.

kubectl create namespace staging
kubectl get pods -n staging
kubectl config set-context --current --namespace=staging

2 Helm — a package manager for Kubernetes

Writing raw YAML for every app, every environment, gets repetitive fast. Helm packages a set of Kubernetes manifests into a reusable "Chart" with templated values — install the same app with different config per environment in one command.

helm install my-release ./my-chart --set replicaCount=3
helm upgrade my-release ./my-chart --set image.tag=2.0
helm rollback my-release 1

3 RBAC — Role-Based Access Control

RBAC defines WHO can do WHAT inside the cluster. A Role lists allowed actions (get, list, create, delete) on specific resource types; a RoleBinding grants that Role to a specific user or service account.

# role.yaml — can only read Pods in this namespace
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
💡 Principle of least privilege applies here exactly like file permissions — grant only the specific verbs/resources a user or service account actually needs.

4 Autoscaling — HPA

A HorizontalPodAutoscaler watches a metric (usually CPU%) and automatically adjusts the number of Pod replicas to match real load — scaling up during traffic spikes, back down when it's quiet.

kubectl autoscale deployment my-app --cpu-percent=70 --min=2 --max=10
# Keeps between 2 and 10 replicas, targeting 70% average CPU utilization
⚠️ HPA needs the metrics-server add-on installed to read CPU usage, and your containers need CPU requests set — without both, the autoscaler shows <unknown> and never scales.

5 Readiness & liveness probes

A liveness probe checks "is this container still alive?" — a failure triggers an automatic restart. A readiness probe checks "is this container ready to receive traffic yet?" — until it passes, the Service won't route requests to that Pod. This is what prevents sending live traffic to a Pod that's still starting up.

livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
