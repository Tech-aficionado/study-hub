☸️ Why Kubernetes? Beginner

Docker runs one container. Kubernetes runs — and babysits — thousands of them, across many machines.

1 The problem beyond "docker run"

Docker alone answers "how do I package and run one container." It doesn't answer: What happens when that container crashes at 3am? What if you need 50 copies of it to handle traffic? What if one of your 20 physical servers dies — where do its containers go? What if you need to update the app with zero downtime?

Kubernetes (often shortened "k8s") is a container orchestrator — it answers all of those questions automatically. You describe the END STATE you want ("5 copies of this app, always running"), and Kubernetes continuously works to make reality match that description.

💡 Think of it like an orchestra conductor: a conductor doesn't play any instrument themselves, but ensures every musician (container) is playing the right part, replaces one who falls ill mid-performance, and keeps overall tempo (the desired state) no matter what.

2 Self-healing — the core idea

You never tell Kubernetes "start this container." You tell it "I want 5 of these running, always" (a desired state). A background control loop constantly checks: is reality matching the desired state? If a container crashes, that's now 4 running when 5 were wanted — Kubernetes notices and starts a replacement automatically, with no human involved.

3 When you actually need it

  • Running the same app across many physical/virtual machines, needing automatic failover.
  • Scaling up/down based on real traffic, automatically.
  • Zero-downtime deployments — rolling out a new version without dropping requests.
  • Managing dozens/hundreds of interconnected services (a "microservices" architecture).
⚠️ Kubernetes is genuinely complex. A single app on a single server almost never needs it — plain Docker (or Docker Compose) is the right tool there. k8s earns its complexity at scale, not before.
