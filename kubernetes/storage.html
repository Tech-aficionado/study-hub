💾 Storage (PV / PVC) Advanced

How data survives beyond a Pod — the claim/volume split, StorageClasses, and the access modes that trip people up.

1 Ephemeral vs persistent

A container's own filesystem is wiped on restart. An emptyDir volume lives as long as the Pod (survives a container crash, shared between the Pod's containers) but dies with the Pod. For data that must outlive the Pod — databases, uploads — you need a PersistentVolume.

2 PV, PVC, StorageClass — the three objects

  • PersistentVolume (PV) — a piece of real cluster storage (a cloud disk, NFS share, local disk). Cluster-scoped.
  • PersistentVolumeClaim (PVC) — a Pod's request for storage ("10Gi, ReadWriteOnce"). Namespaced. The Pod mounts the PVC, not the PV.
  • StorageClass — a template describing a kind of storage (which provisioner, which disk type) so PVs are created on demand.

3 Dynamic provisioning — the normal path

You rarely create PVs by hand. You create a PVC referencing a StorageClass; the StorageClass's provisioner dynamically creates a matching PV (and the real cloud disk) and binds it. Delete the PVC and, depending on the reclaim policy, the disk is deleted too.

apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: db-data }
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: fast-ssd      # omit to use the cluster's default SC
  resources:
    requests: { storage: 20Gi }
# mount it in a Pod
spec:
  volumes:
    - name: data
      persistentVolumeClaim: { claimName: db-data }
  containers:
    - name: db
      volumeMounts:
        - { name: data, mountPath: /var/lib/postgresql/data }
💡 A PVC stuck in Pending usually means: no default StorageClass set, the named StorageClass doesn't exist, or no PV can satisfy the request. kubectl describe pvc shows the reason.

4 Access modes — the classic gotcha

ModeShortMeaning
ReadWriteOnceRWOMounted read-write by a single node (multiple Pods on that node can share it)
ReadOnlyManyROXMounted read-only by many nodes
ReadWriteManyRWXMounted read-write by many nodes (needs NFS/CephFS-type storage)
ReadWriteOncePodRWOPRead-write by exactly one Pod (v1.22+)
⚠️ Most cloud block disks (EBS, PD) are RWO only — one node at a time. Trying to spread a RWO-backed Deployment across nodes leaves Pods stuck ContainerCreating (volume multi-attach error). Need shared read-write across nodes? You need a file storage class (RWX), not a block disk.

5 Reclaim policy & volume binding mode

  • reclaimPolicy on the PV/StorageClass: Delete (default for dynamic — removes the disk when the PVC is deleted) or Retain (keeps the disk + data for manual recovery). Use Retain for anything you can't afford to lose.
  • volumeBindingMode: Immediate provisions as soon as the PVC is created; WaitForFirstConsumer waits until a Pod using it is scheduled, so the disk lands in the same zone as the Pod — essential in multi-zone clusters.
  • allowVolumeExpansion: true lets you grow a PVC later by editing its requested size.
