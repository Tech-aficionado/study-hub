🌐 Services & Networking Intermediate

Pods come and go, with new random IPs each time — Services give them a stable address.

1 Why you need a Service

Pods are disposable — every time one restarts or a Deployment scales, it gets a brand new internal IP. If other Pods tried to talk to a Pod directly by IP, that connection breaks constantly. A Service gives a STABLE address (a name + virtual IP) that automatically routes to whichever healthy Pods currently match a label selector.

2 The three Service types

TypeReachable fromTypical use
ClusterIP (default)Only inside the clusterInternal service-to-service communication
NodePortAny node's IP, on a fixed portSimple external access, mostly dev/testing
LoadBalancerA real external IP (via cloud provider)Production internet-facing traffic
# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  type: ClusterIP
  selector:
    app: my-app
  ports:
    - port: 80
      targetPort: 8080

3 DNS — calling a Service by name

Kubernetes runs an internal DNS server. Any Pod can reach a Service just by its name (my-app-service, or fully qualified my-app-service.default.svc.cluster.local) — no need to hunt down IP addresses manually.

4 Ingress — routing HTTP(S) traffic by hostname/path

A LoadBalancer Service gives ONE Service a public IP. If you have many services behind one domain (api.example.com, app.example.com/admin), an Ingress sits in front and routes by hostname/path to the right internal Service — like a single smart reverse-proxy for the whole cluster.
