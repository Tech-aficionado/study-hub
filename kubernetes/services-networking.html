🌐 Services & DNS Intermediate

Pods come and go with new IPs each time — Services give them a stable address, and DNS gives that address a name.

1 Why you need a Service

Pods are disposable — every restart or scale gives a Pod a new internal IP. If callers used Pod IPs directly, every reschedule would break them. A Service is a stable virtual IP + DNS name that load-balances across whatever healthy Pods currently match its label selector.

2 The Service types

TypeReachable fromUse
ClusterIP (default)Inside the cluster onlyInternal service-to-service
NodePortAny node's IP on a fixed port (30000–32767)Simple external access, dev/testing
LoadBalancerA real external IP from the cloudProduction internet-facing
ExternalNameDNS CNAME to an external hostAlias an outside service by in-cluster name
Headless (clusterIP: None)DNS returns Pod IPs directlyStatefulSets, client-side load balancing

They nest: a NodePort is a ClusterIP plus a node port; a LoadBalancer is a NodePort plus a cloud LB in front.

apiVersion: v1
kind: Service
metadata: { name: my-app }
spec:
  type: ClusterIP
  selector: { app: my-app }
  ports:
    - port: 80            # the Service's port
      targetPort: 8080     # the container's port

3 Headless & ExternalName — the two special cases

Headless (clusterIP: None): no virtual IP, no proxying. DNS returns the individual Pod IPs, so the caller sees every backend and can do its own balancing or address a specific one. This is what gives StatefulSet Pods their pod-0.svc... names.

ExternalName: no selector, no Pods — it maps the Service name to an external DNS name via a CNAME. Lets in-cluster code call payments while it actually resolves to payments.vendor.com, so you can swap the target without touching the app.

apiVersion: v1
kind: Service
metadata: { name: payments }
spec:
  type: ExternalName
  externalName: payments.vendor.com

4 Cluster DNS — calling a Service by name

CoreDNS runs in the cluster and gives every Service a name. From a Pod:

  • my-app — same namespace (short name)
  • my-app.staging — Service in another namespace
  • my-app.staging.svc.cluster.local — fully-qualified

The pattern is <service>.<namespace>.svc.cluster.local. Never hardcode IPs — names are stable, IPs are not.

kubectl run tmp --rm -it --image=busybox:1.36 -- sh
# inside:
nslookup my-app
wget -qO- http://my-app.staging/

5 Endpoints & EndpointSlices — the wiring behind a Service

A Service's selector doesn't route traffic by itself. The EndpointSlice controller watches for matching, Ready Pods and records their IP:port into EndpointSlice objects; kube-proxy (or a CNI dataplane) programs the node so Service traffic is spread across those endpoints.

kubectl get endpointslices -l kubernetes.io/service-name=my-app
kubectl describe svc my-app     # "Endpoints:" line lists backing Pod IPs

EndpointSlices replaced the single monolithic Endpoints object (which didn't scale past thousands of Pods) by sharding endpoints across many small objects.

⚠️ "Service exists but nothing responds" is almost always empty endpoints: the selector matches no Pods, the Pods aren't passing their readiness probe, or targetPort doesn't match the real container port. kubectl get endpointslices tells you instantly — see the runbook.
