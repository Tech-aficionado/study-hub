⏱️ Jobs & CronJobs Intermediate

Run-to-completion work and scheduled work — the batch side of Kubernetes.

1 Jobs — run until it succeeds, then stop

A Deployment keeps Pods running forever. A Job runs a Pod to completion: it retries on failure, and once the required number of Pods have exited successfully, the Job is Complete and nothing restarts. Use it for migrations, backups, one-off imports, batch processing.

apiVersion: batch/v1
kind: Job
metadata: { name: migrate }
spec:
  backoffLimit: 4           # retries before marking the Job Failed
  activeDeadlineSeconds: 600 # hard wall-clock cap
  template:
    spec:
      restartPolicy: OnFailure   # Jobs require OnFailure or Never
      containers:
        - name: migrate
          image: myapp:1.0
          command: ["python", "manage.py", "migrate"]
⚠️ A Job's Pod template must set restartPolicy: OnFailure or Never — not Always (which is for long-running Deployments). backoffLimit counts failed retries; activeDeadlineSeconds is a wall-clock stop regardless of retries.

2 Parallel Jobs — completions & parallelism

PatternFieldsBehaviour
Single task(none)One Pod runs once to success
Fixed countcompletions: NN successful completions needed
Parallel fixedcompletions: N, parallelism: MUp to M Pods at once until N succeed
Work queueparallelism: M onlyM workers drain a queue; any success-and-stop ends it

Indexed Jobs (completionMode: Indexed) give each Pod a unique index via JOB_COMPLETION_INDEX — handy for sharding a dataset across parallel Pods.

3 CronJobs — Jobs on a schedule

A CronJob creates a Job on a cron schedule (UTC by default; set spec.timeZone for a specific zone). Perfect for nightly backups, report generation, cleanup.

apiVersion: batch/v1
kind: CronJob
metadata: { name: nightly-backup }
spec:
  schedule: "0 2 * * *"          # 02:00 every day
  timeZone: "Europe/Berlin"
  concurrencyPolicy: Forbid       # don't start a run if the last is still going
  startingDeadlineSeconds: 120
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: myapp:1.0
              command: ["sh", "-c", "pg_dump ... | gzip > /backup/db.sql.gz"]

4 concurrencyPolicy and the gotchas

  • Allow (default) — overlapping runs are fine.
  • Forbid — skip the new run if the previous is still running.
  • Replace — kill the running one and start the new.

History limits (successfulJobsHistoryLimit / failedJobsHistoryLimit) keep old Job/Pod objects for log inspection — too high and they clutter the namespace, 0 deletes immediately. If the controller is down past startingDeadlineSeconds, a missed run is skipped rather than fired late.

kubectl get cronjob
kubectl get jobs --watch
kubectl create job --from=cronjob/nightly-backup manual-run-1   # trigger now
kubectl logs job/manual-run-1
💡 CronJobs guarantee at-least-once, not exactly-once — a run can occasionally fire twice. Make scheduled work idempotent (safe to run twice) rather than assuming it runs exactly once.
