📈 Autoscaling Advanced

Three autoscalers at three layers: more Pods, bigger Pods, more nodes.

1 Three autoscalers, three jobs

AutoscalerScalesAxis
HPA — Horizontal Pod AutoscalerNumber of Pod replicasOut / in
VPA — Vertical Pod AutoscalerEach Pod's requests/limitsUp / down
Cluster AutoscalerNumber of nodesAdd / remove machines

They compose: HPA adds Pods; when Pods can't be scheduled for lack of room, the Cluster Autoscaler adds a node. VPA right-sizes a single Pod and generally should not be used on the same workload as HPA-on-CPU (they fight).

2 metrics-server is the prerequisite

HPA (on CPU/memory) and kubectl top both read live usage from the metrics-server add-on. It is NOT installed by default on most clusters. Without it, HPA shows <unknown> for the metric and never scales.

kubectl top nodes        # works only if metrics-server is installed
kubectl top pods
# minikube: minikube addons enable metrics-server

3 HPA — the one you'll use

The HPA watches a metric and adjusts replicas to keep it near a target. It also needs the Pods to have CPU/memory requests set (the % target is relative to the request).

# quick imperative form
kubectl autoscale deployment web --cpu-percent=70 --min=2 --max=10
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: web }
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }

The autoscaling/v2 API adds memory, multiple metrics, custom/external metrics (e.g. queue length via an adapter), and behavior blocks to tune scale-up/down rate and stabilization windows (to stop flapping).

⚠️ Two HPA gotchas: it needs requests set (no request = no percentage to compute), and it needs metrics-server (or a custom-metrics adapter) running. "HPA stuck at min replicas / <unknown>" is almost always one of those two.

4 VPA and Cluster Autoscaler

  • VPA recommends (or auto-applies) better requests/limits based on observed usage. In Auto mode it currently has to recreate the Pod to change resources (in-place resize is maturing). Great for right-sizing batch/stateful workloads you can't easily scale horizontally.
  • Cluster Autoscaler watches for Pods stuck Pending because no node has room, and asks the cloud to add a node; it also removes under-utilised nodes (draining them first). It respects PodDisruptionBudgets so scale-down doesn't violate availability.
  • Karpenter (AWS, now broader) is a popular alternative to Cluster Autoscaler that provisions right-sized nodes directly from pending Pods, faster and more flexibly.
💡 Interview framing: "scale the app" = HPA (more replicas) or VPA (bigger replicas); "scale the cluster" = Cluster Autoscaler/Karpenter (more nodes). They operate at different layers and are usually used together.
