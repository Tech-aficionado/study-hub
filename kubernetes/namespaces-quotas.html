🗂️ Namespaces & quotas Intermediate

Carve one cluster into isolated sections, and cap how much each one can consume.

1 Namespaces — virtual clusters

A Namespace partitions a physical cluster into logical sections (dev, staging, prod, per-team). Names only need to be unique within a namespace, and RBAC/quotas/network policies can be scoped per namespace.

kubectl create namespace staging
kubectl get pods -n staging
kubectl get ns
kubectl config set-context --current --namespace=staging  # make it the default

Default namespaces: default (your stuff if you don't choose), kube-system (control-plane add-ons — don't touch), kube-public, kube-node-lease.

2 What a namespace does NOT isolate

  • Not a security boundary by default — without NetworkPolicies, Pods in different namespaces can still talk to each other over the Pod network.
  • Cluster-scoped objects aren't namespaced — Nodes, PersistentVolumes, StorageClasses, ClusterRoles, and CRDs live outside any namespace.
  • DNS crosses namespaces — reach another namespace's Service as svc.other-ns.
kubectl api-resources --namespaced=true    # what IS namespaced
kubectl api-resources --namespaced=false   # what is cluster-scoped

3 ResourceQuota — cap a namespace's total consumption

A ResourceQuota limits the aggregate resources a namespace may use — total CPU/memory requests & limits, and object counts. Once a quota exists, every Pod in that namespace must declare the constrained resources or it's rejected.

apiVersion: v1
kind: ResourceQuota
metadata: { name: team-quota, namespace: staging }
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.cpu: "20"
    limits.memory: 40Gi
    pods: "50"
    persistentvolumeclaims: "10"
kubectl describe resourcequota team-quota -n staging   # used vs hard
⚠️ With a ResourceQuota on requests/limits in place, a Pod that omits them is rejected. Pair the quota with a LimitRange that injects defaults, so developers aren't forced to annotate every Pod by hand.

4 LimitRange — per-object min/max/default

Where ResourceQuota caps the namespace total, a LimitRange governs each Pod/Container: default requests/limits when omitted, and enforced min/max so no single Pod hogs or under-requests.

apiVersion: v1
kind: LimitRange
metadata: { name: constraints, namespace: staging }
spec:
  limits:
    - type: Container
      default: { cpu: 500m, memory: 512Mi }
      defaultRequest: { cpu: 100m, memory: 128Mi }
      max: { cpu: "2", memory: 2Gi }
      min: { cpu: 50m, memory: 64Mi }
💡 The standard multi-tenant recipe: one Namespace per team + a ResourceQuota (total budget) + a LimitRange (sane per-Pod defaults & bounds) + RBAC (who can act in it) + optionally a default-deny NetworkPolicy. That stack turns a shared cluster into safely-isolated tenants.
