🗃️ StatefulSets Advanced

For apps where each replica has a stable identity and its own disk — databases, queues, clustered stores.

1 When a Deployment isn't enough

Deployment Pods are interchangeable and get random names/IPs — perfect for stateless web apps. But a database replica needs: a stable network name (so peers can find it), its own persistent disk (that follows it across restarts), and ordered, predictable startup/scaling. A StatefulSet provides exactly those three guarantees.

2 Stable identity: ordinals and a headless Service

StatefulSet Pods are named <name>-0, <name>-1, … — stable across reschedules. Paired with a headless Service (clusterIP: None), each Pod gets a stable DNS name:

web-0.web.default.svc.cluster.local
web-1.web.default.svc.cluster.local

So db-0 can always reach db-1 by name no matter how many times either restarts — the thing clustered databases need and Deployments can't give.

3 Per-Pod storage with volumeClaimTemplates

A StatefulSet declares a volumeClaimTemplates; Kubernetes creates a separate PVC per Pod (data-web-0, data-web-1…). When web-0 is rescheduled, it reattaches to its own PVC — the data follows the identity.

apiVersion: apps/v1
kind: StatefulSet
metadata: { name: web }
spec:
  serviceName: web          # the headless Service
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
        - name: web
          image: nginx
          volumeMounts:
            - { name: data, mountPath: /usr/share/nginx/html }
  volumeClaimTemplates:
    - metadata: { name: data }
      spec:
        accessModes: [ReadWriteOnce]
        resources: { requests: { storage: 1Gi } }
⚠️ Deleting a StatefulSet does not delete its PVCs by default — that protects your data, but means orphaned PVCs linger until you remove them. (A persistentVolumeClaimRetentionPolicy can automate this.)

4 Ordered operations

  • Scale up / create: Pods come up one at a time in order (0, then 1, then 2), each waiting until the previous is Running and Ready.
  • Scale down / delete: in reverse order (highest ordinal first).
  • Rolling update: reverse order too, one Pod at a time; partition in the update strategy lets you stage a canary by only updating ordinals ≥ N.

Set podManagementPolicy: Parallel if your app doesn't need ordering and you want faster scaling.

💡 Running a database in Kubernetes is usually done via a purpose-built Operator (e.g. for PostgreSQL, Kafka), which uses StatefulSets under the hood but adds backups, failover and version upgrades. StatefulSet is the primitive; the Operator is the production experience.
