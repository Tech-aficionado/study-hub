📊 Resources & QoS Intermediate → Advanced

requests vs limits decide where Pods land, who gets throttled, and who gets killed first under pressure.

1 requests vs limits

  • requests — the amount the container is guaranteed. The scheduler uses requests to decide which node has room; a node is "full" when the sum of requests meets its capacity, regardless of actual usage.
  • limits — the hard ceiling the container may use. The kubelet/runtime enforces it at runtime.
resources:
  requests:
    cpu: "250m"       # 0.25 of a core
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"

CPU is measured in millicores (1000m = 1 core); memory in bytes with Ki/Mi/Gi (power-of-two) suffixes.

2 CPU is throttled, memory is killed

The two resources behave completely differently at their limit — this is the single most important thing to internalise:

  • CPU over limit → throttled. CPU is compressible: the container is slowed down (CFS throttling), never killed. Symptom = latency, not a crash.
  • Memory over limit → OOMKilled. Memory is incompressible: exceed the limit and the kernel OOM-kills the container (exit code 137). The kubelet restarts it (per restartPolicy), so repeated OOM shows as restarts and often CrashLoopBackOff.
⚠️ Setting a memory limit too low for real traffic is the most common self-inflicted OOMKill. Watch actual usage (kubectl top pod) before pinning limits, and leave headroom above the real peak.

3 QoS classes — who gets evicted first

Kubernetes derives a Quality of Service class from how you set requests/limits. Under node memory pressure, the kubelet evicts in QoS order (BestEffort first, Guaranteed last).

ClassConditionEviction priority
GuaranteedEvery container has requests == limits for both CPU & memoryLast (most protected)
BurstableAt least one request set, but not GuaranteedMiddle
BestEffortNo requests or limits at allFirst (evicted soonest)
💡 For critical workloads, set requests == limits (Guaranteed). For bursty web apps, Burstable (request the floor, allow bursting to a higher limit) is usually the right trade-off. Never leave production Pods BestEffort.

4 Diagnosing OOMKilled

kubectl get pod my-pod -o jsonpath='{.status.containerStatuses[0].lastState}'
# → terminated reason: OOMKilled, exitCode: 137
kubectl describe pod my-pod        # Last State: Terminated, Reason: OOMKilled
kubectl top pod my-pod             # live usage vs your limit

Fixes: raise the memory limit if the app legitimately needs it; fix a leak if usage climbs forever; or lower concurrency/caches inside the app. Exit code 137 = 128 + 9 (SIGKILL) — the fingerprint of an OOM kill.

5 LimitRange & defaults

A LimitRange (per namespace) can inject default requests/limits into Pods that omit them, and enforce min/max — so a forgetful developer doesn't ship a BestEffort Pod into a shared namespace. It pairs with ResourceQuota (see Namespaces & quotas).

apiVersion: v1
kind: LimitRange
metadata: { name: defaults }
spec:
  limits:
    - type: Container
      default: { cpu: 500m, memory: 512Mi }       # applied if limits omitted
      defaultRequest: { cpu: 250m, memory: 256Mi } # applied if requests omitted
