🔑 RBAC & ServiceAccounts Advanced

Who can do what, to which resources — the cluster's whole authorization story, built from four object types.

1 The four pieces

RBAC (Role-Based Access Control) answers "is this identity allowed to perform this verb on this resource?" It's assembled from a what (Role) bound to a who (via a Binding):

ObjectScopeSays
RoleOne namespaceAllowed verbs on resources in that namespace
ClusterRoleWhole clusterAllowed verbs, cluster-wide or on cluster-scoped resources (nodes, PVs)
RoleBindingOne namespaceGrants a Role (or ClusterRole) to subjects in that namespace
ClusterRoleBindingWhole clusterGrants a ClusterRole to subjects cluster-wide
💡 A ClusterRole bound by a RoleBinding is the useful combo for reusable permission sets: define "pod-reader" once as a ClusterRole, then RoleBind it per namespace. RBAC is purely additive — there are no deny rules; access defaults to denied.

2 A Role and a binding

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { namespace: staging, name: pod-reader }
rules:
  - apiGroups: [""]                 # "" = the core API group
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { namespace: staging, name: read-pods }
subjects:
  - kind: User
    name: alice
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

Verbs are the API operations: get list watch create update patch delete deletecollection. Resources can go finer-grained (pods/exec, pods/log) and even to named objects with resourceNames.

3 ServiceAccounts — identity for Pods

Users (humans) authenticate externally; ServiceAccounts are the in-cluster identity that Pods run as, so a Pod can call the Kubernetes API with scoped permissions. Every Pod gets the namespace's default ServiceAccount unless you set one.

kubectl create serviceaccount deployer -n ci
# use it in a Pod/Deployment:
spec:
  serviceAccountName: deployer

Modern clusters mount a short-lived, audience-bound projected token (TokenRequest API) rather than a never-expiring Secret, and you can turn the automount off for Pods that don't call the API:

spec:
  automountServiceAccountToken: false   # Pod doesn't need API access

4 Testing & least privilege

kubectl auth can-i list pods -n staging                      # as yourself
kubectl auth can-i create deployments --as=alice -n staging  # impersonate
kubectl auth can-i --list -n staging                         # everything you can do
🚨 The two cardinal RBAC sins: binding cluster-admin to a ServiceAccount "to make it work", and granting get/list on Secrets cluster-wide. Both turn a single compromised Pod into cluster takeover. Scope every grant to the exact verbs, resources, and namespace actually needed, and prefer per-app ServiceAccounts over the shared default.
