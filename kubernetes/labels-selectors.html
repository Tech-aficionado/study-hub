🏷️ Labels & selectors Intermediate

Labels are how everything in Kubernetes finds everything else — Services, Deployments, and your own queries all run on them.

1 Labels vs annotations — different jobs

Both are key/value metadata on an object, but they serve opposite purposes:

  • Labels are identifying and selectable — Kubernetes queries and groups objects by them. Keep them short and meaningful (app, tier, env).
  • Annotations are non-identifying and not selectable — arbitrary extra data for humans and tools (build info, change-cause, ingress controller settings). They can be large.
metadata:
  labels:
    app: payments
    tier: backend
    environment: prod
  annotations:
    kubernetes.io/change-cause: "rollout v2.3.1"
    prometheus.io/scrape: "true"

2 Why selectors are load-bearing

A Service doesn't know about Pods by name — it has a label selector and routes to whatever Pods currently match. A Deployment's spec.selector is how it finds the Pods it owns. Get a label wrong and the Service has zero endpoints or the Deployment adopts the wrong Pods.

3 Equality vs set-based selectors

Services and ReplicationControllers use simple equality selectors. Deployments, ReplicaSets, and kubectl -l also support richer set-based selectors.

# equality-based (CLI)
kubectl get pods -l app=web
kubectl get pods -l 'app=web,tier=front'   # AND

# set-based (CLI)
kubectl get pods -l 'env in (prod,staging)'
kubectl get pods -l 'tier notin (cache)'
kubectl get pods -l 'app'                   # key exists
kubectl get pods -l '!canary'               # key does NOT exist

In YAML, a Deployment selector uses matchLabels and/or matchExpressions:

selector:
  matchLabels:
    app: web
  matchExpressions:
    - { key: tier, operator: In, values: [front, edge] }
    - { key: track, operator: NotIn, values: [canary] }
⚠️ A Deployment's spec.selector is immutable after creation, and it must match the Pod template's labels. A selector/template mismatch is rejected at apply time — a very common first-YAML error.

4 The recommended common labels

Kubernetes defines a standard set under the app.kubernetes.io/ prefix so tools (Helm, dashboards, Argo) can understand any app the same way:

metadata:
  labels:
    app.kubernetes.io/name: payments
    app.kubernetes.io/instance: payments-prod
    app.kubernetes.io/version: "2.3.1"
    app.kubernetes.io/component: api
    app.kubernetes.io/part-of: shop
    app.kubernetes.io/managed-by: helm
💡 Prefix labels/annotations with a DNS domain you control (example.com/team) for your own keys. The bare kubernetes.io/ and k8s.io/ prefixes are reserved for Kubernetes itself.

5 Editing labels live

kubectl label pod my-pod track=canary          # add
kubectl label pod my-pod track=stable --overwrite
kubectl label pod my-pod track-                 # remove (trailing dash)
kubectl get pods --show-labels
💡 Relabelling is a real debugging trick: change a broken Pod's app label so the Service stops routing to it, and the Deployment immediately spins up a healthy replacement — the broken Pod stays alive for you to inspect.
