🚪 Ingress & Gateway API Advanced

One public entry point that routes HTTP(S) by hostname and path to many internal Services — plus its modern successor.

1 The problem Ingress solves

A LoadBalancer Service gives one Service a public IP — ten services means ten load balancers and ten IPs. Ingress puts a single HTTP reverse proxy in front of the cluster and routes by host and path to the right internal (ClusterIP) Service, so one IP + one certificate serves everything.

2 Ingress needs an Ingress Controller

Critically, the Ingress object is just rules — it does nothing on its own. You must install an Ingress Controller (ingress-nginx, Traefik, HAProxy, or a cloud one) that watches Ingress objects and actually serves the traffic. No controller = your Ingress is ignored.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
spec:
  ingressClassName: nginx
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: { name: api, port: { number: 80 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: app, port: { number: 80 } }
  tls:
    - hosts: [shop.example.com]
      secretName: shop-tls
⚠️ Use networking.k8s.io/v1 — the old extensions/v1beta1 and networking.k8s.io/v1beta1 were removed in v1.22. In v1, pathType is required (Prefix, Exact, or ImplementationSpecific) and the backend is service.name + service.port.

3 TLS and the controller-specific bits

Put a cert+key in a kubernetes.io/tls Secret and reference it in spec.tls; most clusters use cert-manager to issue/renew Let's Encrypt certs automatically. Behaviour beyond basic routing (rewrites, rate limits, auth) is set via controller-specific annotations — and those annotations are exactly the pain point the Gateway API fixes.

4 Gateway API — the successor

The Gateway API (gateway.networking.k8s.io, GA since v1.0 / 2023) is the next-generation, more expressive, role-oriented replacement for Ingress. It splits one overloaded object into several:

  • GatewayClass — the kind of gateway (who implements it), set up by the infra provider.
  • Gateway — an actual listener (ports, protocols, TLS), owned by cluster operators.
  • HTTPRoute (and TCPRoute/GRPCRoute) — the routing rules, owned by app developers, attached to a Gateway.
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: shop }
spec:
  parentRefs: [{ name: prod-gateway }]
  hostnames: ["shop.example.com"]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /api } }]
      backendRefs: [{ name: api, port: 80 }]

Why it matters: standard, portable header-based routing, traffic splitting (weights), and cross-namespace references are first-class fields instead of per-controller annotations. Weighted backendRefs make canary a native capability.

💡 Interview-ready summary: Ingress is L7 HTTP routing via one object + annotations; Gateway API is the newer, role-separated, more expressive standard (GatewayClass/Gateway/HTTPRoute) with built-in traffic splitting. New clusters increasingly prefer Gateway API; Ingress remains widely deployed.
