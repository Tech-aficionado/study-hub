📦 Pods in depth Intermediate

The smallest thing Kubernetes schedules — its lifecycle, restart rules, and the helper-container patterns that live inside it.

1 What a Pod really is

Kubernetes never schedules a bare container — the smallest deployable unit is a Pod: one or more containers that always run together on the same node, sharing a network namespace (same IP + port space, so they reach each other on localhost) and able to share storage volumes. Usually a Pod holds exactly one container; multiple containers are reserved for genuine helper patterns (card 5).

# pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app-pod
  labels: { app: my-app }
spec:
  containers:
    - name: app
      image: myapp:1.0
      ports:
        - containerPort: 8080
⚠️ A bare Pod has NO self-healing — if its node dies, nothing recreates it. In practice you create Pods indirectly through a Deployment, StatefulSet, DaemonSet or Job, which owns a Pod template and keeps the right Pods running.

2 Pod phases and the status you'll actually read

A Pod's status.phase is a coarse top-level summary; the detail you debug with lives in the container statuses and conditions.

PhaseMeaning
PendingAccepted, but not all containers are running yet — image pulling, or waiting for the scheduler to place it.
RunningBound to a node, all containers created, at least one still running/starting.
SucceededAll containers exited 0 and will not restart (typical for Jobs).
FailedAll containers terminated and at least one failed (non-zero exit, or killed).
UnknownThe node's kubelet can't be reached to report status.

The states you see in kubectl get pods (like CrashLoopBackOff, ImagePullBackOff, OOMKilled, ContainerCreating) are container-level waiting/terminated reasons, not phases — the troubleshooting runbook walks each one.

3 restartPolicy — who restarts, and when

spec.restartPolicy controls the kubelet's restarts of containers within a Pod. It defaults to Always.

  • Always (default) — restart a container whenever it exits, success or failure. Required by Deployments/ReplicaSets.
  • OnFailure — restart only on non-zero exit. Used by Jobs that should retry on error.
  • Never — never restart; the Pod goes Succeeded/Failed. Used by Jobs that must not retry a container in place.

Restarts use exponential back-off (10s, 20s, 40s … capped at 5 min). A container that keeps crashing therefore shows CrashLoopBackOff — the "BackOff" is the kubelet waiting before the next restart.

💡 restartPolicy restarts a container in place on its existing node. Rescheduling a Pod onto a different node is a different mechanism — that only happens for Pods owned by a controller, which creates a brand-new Pod.

4 Init containers — run-to-completion setup

Init containers run one at a time, in order, to completion before any app container starts. If one fails, the kubelet restarts it (subject to the Pod's restartPolicy) until it succeeds — the app containers never start until every init container has exited 0. Use them to wait for a dependency, run a migration, or fetch config.

spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ['sh', '-c', 'until nc -z db 5432; do echo waiting; sleep 2; done']
  containers:
    - name: app
      image: myapp:1.0

5 Multi-container patterns & native sidecars

When a Pod does hold several containers, it is for a tight helper relationship — they share the Pod's network and can share volumes:

  • Sidecar — a long-running helper beside the main app: log shipper, metrics exporter, service-mesh proxy.
  • Ambassador — a proxy that simplifies the app's outbound connections (e.g. a local Redis proxy).
  • Adapter — reshapes the app's output into a standard format (e.g. a logs/metrics adapter).

Since v1.29 (stable in 1.33) Kubernetes has native sidecar containers: declare the helper as an initContainer with restartPolicy: Always. It then starts before the app, keeps running alongside it, and shuts down after it — fixing the old problem of sidecars outliving a Job's main container.

spec:
  initContainers:
    - name: log-shipper
      image: fluent-bit:3.0
      restartPolicy: Always      # ← makes it a native sidecar
  containers:
    - name: app
      image: myapp:1.0
⚠️ Don't cram unrelated services into one Pod to "save Pods". Containers in a Pod scale together and die together. Two things that scale independently belong in two Deployments.
