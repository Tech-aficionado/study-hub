🚀 Deployments in depth Intermediate → Advanced

The object you'll use most — how its rolling update actually moves, how to tune it, undo it, and layer blue-green/canary on top.

1 Deployment → ReplicaSet → Pods

A Deployment manages ReplicaSets, each of which keeps N identical Pods running. You almost never touch a ReplicaSet directly — the Deployment creates a new one for each template change and scales the old one down, which is exactly what gives you rollouts and rollback.

2 RollingUpdate — maxSurge & maxUnavailable

The default strategy is RollingUpdate, tuned by two knobs (each a count or a percentage of replicas):

  • maxSurge (default 25%) — how many extra Pods above the desired count may exist during the update. Higher = faster rollout, more peak resource use.
  • maxUnavailable (default 25%) — how many Pods may be missing below the desired count during the update. 0 = never drop below full capacity.
spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2            # up to 12 Pods briefly
      maxUnavailable: 0       # never below 10 ready → zero-downtime
  minReadySeconds: 10         # a new Pod must stay ready 10s before counting

The other strategy is Recreate: kill all old Pods, then start new ones — a downtime gap, but necessary when two versions can't run at once (e.g. an incompatible schema migration or a ReadWriteOnce volume).

⚠️ maxSurge and maxUnavailable can't both be 0 — the rollout would have no room to make progress. Kubernetes rejects that combination.

3 Driving and watching a rollout

kubectl set image deployment/web app=myapp:2.0
kubectl rollout status deployment/web        # blocks until done or failed
kubectl rollout pause deployment/web         # freeze mid-rollout (for canary)
kubectl rollout resume deployment/web
kubectl annotate deployment/web kubernetes.io/change-cause="bump to 2.0"

A new rollout only triggers when the Pod template changes (image, env, labels…). Changing just replicas scales in place and does not create a new ReplicaSet.

4 History & rollback

kubectl rollout history deployment/web
kubectl rollout history deployment/web --revision=3   # detail of one revision
kubectl rollout undo deployment/web                   # back to previous
kubectl rollout undo deployment/web --to-revision=2   # to a specific one

Each revision is an old ReplicaSet kept around (scaled to 0). spec.revisionHistoryLimit (default 10) controls how many are retained. The CHANGE-CAUSE column comes from the kubernetes.io/change-cause annotation — set it on every deploy so history is readable.

💡 Rollback is near-instant because the old ReplicaSet still exists — undo just scales the old one back up and the new one down. That's why you don't delete old ReplicaSets by hand.

5 Blue-green and canary

A plain Deployment does rolling updates. Two richer release patterns are built from Deployments + Services + labels:

  • Blue-green — run two full Deployments (blue = current, green = new). Both are up; the Service selector points at blue. Flip the selector to green to cut over instantly, flip back to roll back. Costs double capacity during the switch.
  • Canary — send a small slice of traffic to the new version first. Simplest form: one Service selecting a shared label (app=web) across a large stable Deployment and a tiny canary Deployment, so the canary gets replicas-proportional traffic. For percentage-precise splits, an Ingress controller or a service mesh (Istio/Linkerd) or Argo Rollouts does weighted routing.
# blue-green cutover: just change which version the Service selects
kubectl patch service web -p '{"spec":{"selector":{"app":"web","version":"green"}}}'
⚠️ Blue-green and precise canary are patterns you assemble, not a Deployment field. If an interviewer asks "how do you do canary in Kubernetes", the honest answer names the building blocks (labels + Service, or Ingress/mesh weights, or Argo Rollouts) — a bare Deployment can't weight traffic by percentage.
