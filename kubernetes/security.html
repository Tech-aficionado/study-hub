🛡️ Pod security & NetworkPolicy Advanced

Hardening the Pod itself, enforcing baseline standards, and locking down Pod-to-Pod traffic.

1 securityContext — hardening a container

A securityContext (per-Pod or per-container) controls the privileges the container runs with. A hardened baseline:

spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    fsGroup: 2000
  containers:
    - name: app
      image: myapp:1.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        privileged: false
        capabilities:
          drop: ["ALL"]
  • runAsNonRoot / runAsUser — don't run as root in the container.
  • allowPrivilegeEscalation: false — can't gain more privileges than the parent.
  • readOnlyRootFilesystem: true — immutable rootfs; writes go to explicit volumes only.
  • capabilities.drop: ["ALL"] — strip Linux capabilities, add back only what's needed.
  • privileged: false — a privileged container is near-equivalent to root on the node; almost never needed.

2 Pod Security Standards & Admission

The old PodSecurityPolicy was removed in v1.25. Its replacement is Pod Security Admission (PSA), a built-in admission controller enforcing the three Pod Security Standards at the namespace level:

StandardAllows
privilegedUnrestricted — anything
baselineBlocks the known-dangerous (privileged, host namespaces, most host mounts)
restrictedHeavily hardened — enforces runAsNonRoot, drop ALL caps, seccomp, etc.

You opt a namespace in with labels, choosing a mode per standard: enforce (reject), audit (log), warn (warn on apply).

kubectl label ns prod \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted
💡 For policies beyond the three built-in levels (custom rules, image-registry allowlists, required labels), reach for a policy engine like Kyverno or OPA/Gatekeeper as a validating admission webhook.

3 NetworkPolicy — a firewall for Pods

By default all Pods can talk to all Pods, across namespaces. A NetworkPolicy restricts ingress/egress by label selector — but only if your CNI enforces it (Calico, Cilium do; some basic ones don't). Policies are additive and allow-list based.

The foundational move is a default-deny, then open exactly what's needed:

# deny all ingress in this namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-ingress, namespace: prod }
spec:
  podSelector: {}            # all Pods
  policyTypes: [Ingress]
# then allow only the frontend to reach the api on 8080
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: api-from-frontend, namespace: prod }
spec:
  podSelector: { matchLabels: { app: api } }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector: { matchLabels: { app: frontend } }
      ports:
        - { protocol: TCP, port: 8080 }
⚠️ Two traps: (1) a NetworkPolicy only takes effect if the CNI supports it — on a cluster whose CNI ignores policies, the YAML applies cleanly but enforces nothing. (2) As soon as any policy selects a Pod, that Pod is default-deny for the covered direction — forget an egress rule for DNS and your Pods can't resolve names.

4 Image & supply-chain hygiene

  • Pin image digests (@sha256:...) or specific tags, never :latest in production.
  • Scan images for CVEs in CI (Trivy, Grype) and sign/verify them (cosign + admission policy).
  • Use minimal base images (distroless, Alpine) to shrink the attack surface.
  • Encrypt Secrets at rest and keep them out of images and Git (see ConfigMaps & Secrets).
💡 The "4C's of cloud-native security" interview framing: Cloud, Cluster, Container, Code — each layer secures the one inside it. securityContext/PSA = Container; RBAC/NetworkPolicy = Cluster.
