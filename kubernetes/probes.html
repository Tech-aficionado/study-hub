❤️ Health probes Intermediate

Three probes answer three different questions — mix them up and you cause the outage you were trying to prevent.

1 The three probes

ProbeQuestionOn failure
livenessIs the container wedged and needs a restart?kubelet restarts the container
readinessIs it ready to serve traffic right now?Pod removed from Service endpoints (no restart)
startupHas a slow app finished booting?kubelet keeps waiting; gates the other two until it passes
⚠️ The classic self-inflicted outage: using a liveness probe for readiness logic (e.g. "is the database reachable"). A transient DB blip then restarts every Pod at once instead of just temporarily pulling them from the Service. Readiness removes from traffic; liveness restarts — don't swap them.

2 Probe mechanisms

  • httpGet — a 2xx/3xx on a path = healthy. Most common for web apps.
  • tcpSocket — can we open a TCP connection to a port? Good for non-HTTP servers.
  • exec — run a command inside the container; exit 0 = healthy.
  • grpc — native gRPC health check (v1.24+).
startupProbe:
  httpGet: { path: /healthz, port: 8080 }
  failureThreshold: 30
  periodSeconds: 5        # up to 150s to boot before liveness kicks in
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
  failureThreshold: 1

3 The timing knobs

FieldMeaning
initialDelaySecondsWait this long before the first probe
periodSecondsHow often to probe
timeoutSecondsProbe fails if it takes longer than this
failureThresholdConsecutive failures before acting
successThresholdConsecutive successes to be considered healthy again

4 startupProbe fixes slow starters

A JVM or heavy app can take 60–120s to boot. If you widen the liveness probe's initialDelaySeconds to cover that, you also make real hangs take that long to detect forever. The startupProbe solves this: it holds off liveness/readiness until the app has started once (failureThreshold × periodSeconds = max boot time), then hands over to a tight liveness probe. Slow start AND fast hang-detection — both.

💡 Readiness is also how zero-downtime rollouts work: a new Pod isn't added to the Service until its readiness probe passes, so traffic never hits a half-started Pod. Pair it with minReadySeconds on the Deployment.
