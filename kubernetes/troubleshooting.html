🩺 Troubleshooting runbook Advanced

The five failures you'll actually hit, each with the exact commands to diagnose and the real fix.

1 First four commands, every time

kubectl get pods -o wide                    # status, restarts, node
kubectl describe pod <pod>                   # Events at the bottom are gold
kubectl logs <pod> [--previous] [-c <ctr>]   # app's own errors; --previous for a crashed container
kubectl get events --sort-by=.lastTimestamp # cluster-level timeline

The Events at the bottom of describe name the exact reason (FailedScheduling, Failed, BackOff, Unhealthy). Read them before guessing.

2 Decision tree

3 ImagePullBackOff / ErrImagePull

The kubelet can't pull the image. describe pod → Events shows the exact reason.

  • Wrong name/tag — typo, or a tag that doesn't exist (manifest unknown). Fix the image reference.
  • Private registry, no creds — create a docker-registry Secret and reference it via imagePullSecrets (or on the ServiceAccount).
  • Rate limited (Docker Hub toomanyrequests) — authenticate, or mirror the image.
kubectl create secret docker-registry regcred \
  --docker-server=registry.example.com --docker-username=U --docker-password=P
# then in the Pod spec: imagePullSecrets: [{ name: regcred }]

4 CrashLoopBackOff

The container starts, exits, and the kubelet keeps restarting it with growing back-off. CrashLoop is a symptom, not a cause — the logs hold the cause.

kubectl logs <pod> --previous      # the crashed instance's output
kubectl describe pod <pod>          # Last State → Reason + exit code
  • App error on boot (bad config, missing env/Secret, can't reach a dependency) — fix the config; use an init container to wait for dependencies.
  • Exit 137 = OOMKilled → see card 5.
  • Failing liveness probe restarting a healthy-but-slow app → add a startupProbe (see Probes).
  • Container has no long-running process (exits 0 immediately) — the command returns instead of staying up.

5 Pending, OOMKilled, and "Service but no response"

Pending — the scheduler can't place the Pod. describe pod → Event FailedScheduling gives the reason:

  • Insufficient cpu/memory — requests exceed any node's free capacity. Lower requests, or add nodes (Cluster Autoscaler).
  • had taint ... that the pod didn't tolerate — add a toleration or target other nodes.
  • unbound PersistentVolumeClaim — no StorageClass / PVC can't bind (see Storage).
  • didn't match node affinity/selector — no node has the required labels.

OOMKilled (exit 137) — container exceeded its memory limit. describe pod shows Last State: Terminated, Reason: OOMKilled. Raise the limit if usage is legit, fix a leak if it climbs forever, or lower in-app caches (see Resources & QoS).

Service exists but nothing responds — almost always empty endpoints:

kubectl get endpointslices -l kubernetes.io/service-name=<svc>
kubectl describe svc <svc>      # "Endpoints:" empty? → no Pods backing it
  • Service selector doesn't match the Pods' labels.
  • Pods are failing their readiness probe (not Ready → not an endpoint).
  • targetPort ≠ the real containerPort.
💡 Golden rule: the STATUS column tells you which card to open; describe's Events + logs --previous tell you why. Never fix from the status alone.
