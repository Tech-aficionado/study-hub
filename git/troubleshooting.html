🧯 Troubleshooting Intermediate

The scary-looking Git messages everyone hits, what each actually means, and the exact command to get unstuck.

1 "You are in 'detached HEAD' state"

What happened: you checked out a specific commit or tag instead of a branch, so HEAD points straight at a commit with no branch attached. Commits you make here aren't on any branch and can be lost.

# You're just looking around — go back to a branch:
git switch main

# You made commits here you want to KEEP — put them on a new branch:
git switch -c my-recovered-work
# (do this BEFORE switching away, or find the commit later via git reflog)
Detached HEAD isn't a bug — it's useful for inspecting history or building from an old point. Just make a branch before committing if you want to keep the work.

2 "Updates were rejected... non-fast-forward"

What happened: the remote has commits you don't have locally, so Git won't let your push overwrite them. Someone pushed since you last pulled.

# Correct fix: get their changes, then push
git pull --rebase origin main   # replay your commits on top of theirs
# resolve any conflicts, then:
git push origin main
🛑 Do NOT reach for git push --force as a reflex — it overwrites the teammate's commits that triggered the rejection. If you genuinely must force (e.g. after rebasing your own feature branch), use git push --force-with-lease, which refuses if someone else pushed in the meantime.

3 "refusing to merge unrelated histories"

What happened: you're merging/pulling two repos that have no common ancestor — e.g. you created a repo locally AND initialised one on GitHub with a README, so both have independent root commits.

git pull origin main --allow-unrelated-histories
# Explicitly tell Git it's OK to stitch two separate histories together
# You'll likely resolve a conflict or two, then commit the merge
💡 Avoid it next time: when creating a GitHub repo you'll push an existing local project to, do not tick "add a README" — start it empty so there's no competing root commit.

4 "LF will be replaced by CRLF" warnings

What happened: this is a warning, not an error — Git is normalising line endings per your core.autocrlf setting on Windows. Your commit still works.

# Make the behaviour explicit and team-wide instead of per-machine:
# commit a .gitattributes with:
* text=auto

# To silence the warning entirely (if you understand the trade-off):
git config --global core.safecrlf warn   # or "false" to hide it

5 "I committed to the wrong branch"

# Commit landed on main but belongs on a feature branch, and it's NOT pushed:
git switch -c feature-x        # make the branch here (carries the commit)
git switch main
git reset --hard HEAD~1        # remove it from main (safe: it's safe on feature-x)
⚠️ The reset --hard here is safe only because you first created feature-x pointing at that commit. Always make the new branch before resetting, so the commit is never orphaned.

6 "I think I lost commits" — the universal rescue

Git rarely deletes commits immediately. The reflog records every position HEAD has held — including commits a bad reset seemed to erase. This recovers most "disasters."

git reflog
# e.g.  a1b2c3 HEAD@{1}: commit: the work you thought was gone

git switch -c recovered a1b2c3
# Recover that exact state onto a new branch
💡 Golden habit: when something goes wrong, your first instinct should be git status then git reflog — not panic, and never deleting the .git folder. The information you need is almost always still there.

7 "fatal: not a git repository"

What happened: you're running a Git command in a folder that has no .git directory — either you're in the wrong directory, or the repo was never initialised.

git rev-parse --show-toplevel   # prints the repo root, or errors if none
pwd                              # check where you actually are
git init                         # if this really should be a repo
