🧪 Hands-on Labs

Do these in a real terminal (or try the risk-free steps in the Git Playground first). Each lab builds on the last.

Lab 1 — Beginner Your first repository

  1. Make a folder, cd into it, run git init. Confirm with git status.
  2. Create README.md, then stage and commit it: git add README.md, git commit -m "Add README".
  3. Edit the README, run git diff to see the change, then commit again.
  4. Run git log --oneline --graph. You should see two commits.

Lab 2 — Beginner Staging precision with add -p

  1. In one file, make two unrelated edits (e.g. fix a typo near the top, change a value near the bottom).
  2. Run git add -p. Stage only the first hunk (y), skip the second (n).
  3. Commit the first change, then stage and commit the second separately.
  4. Verify with git log -p that the two changes are in two commits.

Lab 3 — Intermediate Branch, diverge, merge

  1. From main, create and switch: git switch -c feature. Commit a change.
  2. Switch back to main, commit a different change (so the branches diverge).
  3. Merge: git switch main && git merge feature. Since both moved, you get a merge commit.
  4. Confirm the two-parent merge with git log --oneline --graph --all.

Lab 4 — Intermediate Create and resolve a conflict

  1. On main and on a new feature branch, change the same line of the same file to different text.
  2. Merge feature into main — Git reports a CONFLICT.
  3. Open the file, read the <<<<<<< / ======= / >>>>>>> markers, edit to the final content, delete the markers.
  4. git add <file> then git commit to complete the merge. Try git merge --abort on a fresh attempt to see the escape hatch.

Lab 5 — Intermediate Undo three ways

  1. Make and commit a change. Undo it with git revert HEAD — note it creates a new commit.
  2. Make another commit, then git reset --soft HEAD~1 — the change returns to staging.
  3. Commit again, then git reset --mixed HEAD~1 — now it's unstaged but kept in your files.
  4. Run git reflog and recover any state you passed through with git switch -c rescue <hash>.

Lab 6 — Advanced Squash with interactive rebase

  1. Make 4 messy commits on a branch ("wip", "fix", "typo", "actually works").
  2. Run git rebase -i HEAD~4. Keep the first as pick, mark the rest squash (or fixup).
  3. Write one clean combined message. Confirm with git log --oneline that 4 commits became 1.
  4. Reflect: why is this safe to do before pushing but dangerous after?

Lab 7 — Advanced Find a bug with bisect

  1. In a repo with ~10+ commits, pick a "feature" that's now broken but worked earlier.
  2. git bisect start, mark the current commit git bisect bad, an old good one git bisect good <hash>.
  3. Git checks out midpoints — test each, answer good/bad until it names the first bad commit.
  4. git bisect reset to finish. Appreciate that ~1000 commits take only ~10 steps.

Lab 8 — Advanced Tag a release & push it

  1. Annotate a release: git tag -a v1.0.0 -m "First release".
  2. Inspect it: git show v1.0.0. Note the tagger and message.
  3. Push it explicitly: git push origin v1.0.0 (prove to yourself a plain push doesn't send tags).
  4. Run git describe --tags after a couple more commits and read the output format.
