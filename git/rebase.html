♻️ Rebase in Depth Advanced

Replay commits onto a new base, squash messy history interactively, and never break the golden rule.

1 What rebase does

Rebase takes the commits unique to your branch, sets them aside, moves your branch to the tip of another branch, and replays your commits one by one on top. The result is a straight line — as if you'd started your work from the latest main all along.

git switch feature
git rebase main
# Replays feature's commits on top of main's latest commit

git switch main
git merge feature          # now a clean fast-forward

2 The golden rule of rebasing

🛑 Never rebase commits that exist outside your own machine — anything you've pushed and others may have pulled. Rebase creates brand-new commits with new hashes; everyone holding the old commits now has a diverged, conflicting history.

Safe to rebase: your local feature branch before you've pushed it, or a branch only you work on. Unsafe: main, develop, or any shared branch teammates have based work on.

3 Interactive rebase — rewrite your own history

git rebase -i opens an editor listing your recent commits, each prefixed with an action word you can change. This is how you turn 12 messy "wip" commits into one clean, reviewable commit before opening a pull request.

git rebase -i HEAD~4
# Opens an editor with your last 4 commits:

pick   a1b2c3  Add login form
squash d4e5f6  wip
squash g7h8i9  fix typo
reword j0k1l2  Add validation

# Change the FIRST word of each line to choose an action:
ActionEffect
pickKeep the commit as-is
rewordKeep changes, edit the message
editPause here so you can amend the commit's contents
squashFold into the commit above, combine both messages
fixupFold into the commit above, discard this message
dropDelete the commit entirely
reorderMove a line up/down to reorder commits

4 When a rebase hits a conflict

Because rebase replays commits one at a time, a conflict can appear at each replayed commit. Resolve it, stage, then --continue — don't commit manually during a rebase.

# After editing the conflicted file(s):
git add resolved-file.js
git rebase --continue       # proceed to the next commit

git rebase --skip           # drop the commit currently being applied
git rebase --abort          # bail out entirely, back to the pre-rebase state
💡 git pull --rebase fetches the remote's new commits and replays your local commits on top, instead of making a merge commit — keeping a shared branch's history linear. Set it as the default with git config --global pull.rebase true.

5 Rebase vs merge — choosing deliberately

git mergegit rebase
HistoryPreserved exactly, with a merge commitRewritten into a straight line
Commit hashesUnchangedNew (replayed commits)
Safe on shared branches?YesNo — only your own un-pushed work
Best forIntegrating a finished feature; audit trailCleaning up local commits before review
A common team policy: rebase your feature branch onto the latest main to stay current and squash WIP commits, then merge into main with --no-ff so the merge is recorded. You get both a clean feature history and a clear integration point.
