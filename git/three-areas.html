🗂️ Three Areas & Staging Beginner

Working directory, staging area, repository — and the surprisingly powerful art of staging only part of your work.

1 The three areas, and the two commands between them

Think of Git as having three rooms your changes move through. A change starts in your working directory, you git add it into the staging area (also called the index), and git commit seals everything staged into the repository as a permanent snapshot.

2 Reading git status like a pro

git status is the command you run constantly to see which area each change sits in. Learn to read its three sections:

$ git status
On branch main
# Section 1 — STAGED (green): will go into the next commit
Changes to be committed:
  modified:   app.js

# Section 2 — MODIFIED but not staged (red): tracked, edited, not added yet
Changes not staged for commit:
  modified:   style.css

# Section 3 — UNTRACKED: brand-new files Git has never seen
Untracked files:
  notes.txt
git status -s
# Short format. Two columns: left = staging area, right = working dir
#  M app.js   -> staged modification
# M  style.css -> modified, not staged
# ?? notes.txt -> untracked

3 Why staging exists: crafting clean commits

Beginners often ask "why not just commit everything?" The staging area lets you build a commit deliberately. You might have fixed a bug AND renamed a variable in the same editing session — staging lets you commit each as its own clean, reviewable change.

git add app.js            # stage only the bug fix
git commit -m "Fix off-by-one in pagination"

git add style.css          # now stage the unrelated change
git commit -m "Rename --accent to --brand colour variable"
💡 A reviewer thanks you for two focused commits over one giant "misc changes" commit. Future-you, running git bisect to find which change broke something, thanks you even more.

4 git add -p — stage by the chunk, not the file

Sometimes two unrelated changes are in the same file. git add -p (patch mode) walks you through each "hunk" and asks whether to stage it. This is the single biggest upgrade to most people's Git workflow.

git add -p app.js
# Git shows one hunk at a time and asks:
# Stage this hunk [y,n,q,a,d,s,e,?]?
#   y = yes, stage it      n = no, skip it
#   s = split into smaller hunks   e = edit the hunk by hand
#   q = quit                a = stage this and all remaining
The same -p flag works on git restore -p, git stash -p, and git checkout -p — anywhere you want hunk-level control.

5 Unstaging and discarding with git restore

Modern Git (2.23+) split the overloaded old git checkout into two clearer commands: git switch for branches and git restore for files. Use restore to move changes backward through the three areas.

git restore --staged file.txt
# Move file OUT of the staging area, back to "modified" — keeps your edits

git restore file.txt
# ⚠️ Throw away working-directory edits — restores the last committed version

git restore --source=HEAD~2 file.txt
# Restore this file as it was 2 commits ago (into your working dir)
🛑 Plain git restore file.txt permanently discards uncommitted edits. Git never tracked them, so there is nothing to recover. Run git status and git diff first to be sure.
