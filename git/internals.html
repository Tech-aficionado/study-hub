🔬 Git Internals Advanced

Open the hood: blobs, trees, commits, refs and HEAD. Once you see the object graph, Git stops being magic.

1 Git is a content-addressable key-value store

At its core, Git is a simple database: you hand it content, it hashes that content with SHA-1, stores it under that hash, and hands the hash back as the key. Same content always produces the same key — that's what "content-addressable" means. Everything else (branches, history, staging) is built on top of this.

# Store raw content, get its key back (the plumbing command add/commit use)
$ echo 'test content' | git hash-object -w --stdin
d670460b4b4aece5915caf5c68d12f560a9fe3e4

# Read any object back out by its key
$ git cat-file -p d670460b4b4aece5915caf5c68d12f560a9fe3e4
test content

$ git cat-file -t d670460b4b4aece5915caf5c68d12f560a9fe3e4
blob
Objects live in .git/objects/, named by hash: the first 2 characters are the subdirectory, the remaining 38 the filename. Each object is zlib-compressed, with a small <type> <size>\0 header prepended before hashing.

2 The four object types

  • Blob — the raw contents of one file. Stores only the bytes; no filename, no path, no date.
  • Tree — a directory. Lists entries, each being a mode + type + name pointing to a blob (file) or another tree (subdirectory). This is where filenames actually live.
  • Commit — points to one top-level tree (the whole project snapshot), plus parent commit(s), author/committer, and the message.
  • Tag — an annotated tag object: a named, signed pointer to a commit with its own message.
$ git cat-file -p main^{tree}
100644 blob a906cb2a...   README
100644 blob 8f941393...   Rakefile
040000 tree 99f1a6d1...   lib
# A tree lists blobs (files) and sub-trees (folders) by hash
💡 Note what's missing from a blob: Git stores file contents separately from file names. If two files have identical content, Git stores one blob and both tree entries point at it. That's a big part of why Git is so storage-efficient.

3 The object graph

Follow all the internal pointers and you get a directed acyclic graph: a commit points to a tree, the tree points to blobs and sub-trees, and each commit points back to its parent. Nothing is ever stored as a diff — every commit references a complete tree of the project at that moment.

4 Refs and HEAD — how branches really work

A branch is just a 41-byte text file under .git/refs/heads/ containing the hash of one commit. Committing simply rewrites that file to point at the new commit. That's the entire secret to why branching is instant.

$ cat .git/refs/heads/main
g7h8i9a0b1c2d3e4f5...        # a branch IS a pointer to one commit

$ cat .git/HEAD
ref: refs/heads/main         # HEAD usually points at a branch...
# ...and in "detached HEAD" state it holds a raw commit hash instead

$ git symbolic-ref HEAD       # what HEAD currently points to
refs/heads/main
HEAD is "where you are right now." Normally it points at a branch, and that branch points at a commit. Checking out a specific commit (not a branch) detaches HEAD — it points straight at a commit with no branch in between.

5 A tour of the .git folder

.git/
├── HEAD            # current branch pointer
├── config          # this repo's configuration
├── index           # the staging area (binary)
├── objects/        # every blob, tree, commit, tag — the database
│   ├── 1f/7a7a...   # loose object (first 2 hash chars = folder)
│   └── pack/        # many objects compressed together
├── refs/
│   ├── heads/       # local branches (one file each)
│   └── tags/        # tags
└── logs/            # the reflog lives here — HEAD's movement history
⚠️ Delete the .git folder and you delete the entire history — your working files remain, but it's no longer a repository. Everything Git knows lives in this one hidden folder.

6 Packing & garbage collection

Storing every version as a loose file would balloon in size, so Git periodically packs many objects into a single compressed packfile, storing similar objects as deltas against each other. git gc ("garbage collect") does this and prunes unreachable objects.

git gc
# Compress loose objects into packfiles, tidy refs, prune the unreachable

git count-objects -v
# See how many loose vs packed objects you have, and their sizes

git fsck
# Verify the integrity of the object database
💡 Grounded in the official Pro Git — Git Internals chapter: a commit really is just tree + parent(s) + author + message, and git add/git commit are convenience wrappers over hash-object, update-index, write-tree and commit-tree.
