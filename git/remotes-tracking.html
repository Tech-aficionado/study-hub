🔄 Fetch, Pull & Tracking Intermediate

The exact difference between fetch and pull, remote-tracking branches, and keeping a branch in sync without merge-commit noise.

1 Remote-tracking branches: your local snapshot of the remote

When you clone or fetch, Git stores read-only pointers like origin/main — these are remote-tracking branches. They record "where main was on the remote the last time I talked to it." You never commit on them directly; they move only when you fetch.

git branch -a
# -a shows local AND remote-tracking branches:
#   * main                 (your local branch)
#     remotes/origin/main  (snapshot of the remote's main)

git branch -vv
# Each local branch, which remote it tracks, and ahead/behind counts:
#   main  a1b2c3 [origin/main: ahead 2, behind 1] ...

2 fetch vs pull — the crucial distinction

git fetch downloads new commits and updates your remote-tracking branches, but does not touch your working files or current branch. git pull is fetch + an automatic merge (or rebase) of those changes into your branch.

git fetch origin
git log --oneline main..origin/main   # see what's new BEFORE merging
git merge origin/main                 # integrate when you're ready

git pull            # the shortcut: fetch + merge your tracked branch
💡 When a pull does something confusing, slow down: fetch then log main..origin/main shows you exactly what came down before you merge it. "Fetch, look, then merge" prevents most pull surprises.

3 pull --rebase: a linear shared history

A plain git pull that needs to combine your local commits with new remote commits creates a merge commit — producing those "Merge branch 'main' of…" commits that clutter history. pull --rebase replays your local commits on top of the fetched ones instead.

git pull --rebase origin main
# Fetch, then rebase YOUR local commits on top of the remote's — no merge commit

git config --global pull.rebase true
# Make every plain "git pull" rebase by default
⚠️ pull --rebase rewrites your own un-pushed commits, which is safe. It does not rewrite anyone else's — it's replaying your local work, not the shared history.

4 Setting up tracking (upstream)

git push -u origin feature-login
# First push of a new branch: -u links local feature-login to origin/feature-login
# After this, plain "git push" and "git pull" just work on this branch

git branch --set-upstream-to=origin/main main
# Link an existing local branch to a remote one after the fact

git push origin --delete old-feature
# Delete a branch on the remote

5 Managing remotes

git remote -v
# List remotes and their fetch/push URLs

git remote add upstream https://github.com/original/repo.git
# Add a 2nd remote — common when working from a fork (origin = your fork)

git fetch upstream
git merge upstream/main       # pull in changes from the original project

git remote rename origin github
git remote set-url origin git@github.com:user/repo.git  # switch HTTPS → SSH
In an open-source fork workflow, origin is your fork (you push here) and upstream is the original project (you fetch from here to stay current). Keeping these straight is half the battle of contributing.
