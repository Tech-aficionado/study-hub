📜 Basic Workflow Beginner

init, clone, status, add, commit, log — the five commands you'll type a hundred times a day.

1 Starting a repository

Two ways to get a Git repo: start a brand new one, or copy an existing one from somewhere else (like GitHub).

git init
# Turns the current folder into a Git repo (creates a hidden .git folder)

git clone https://github.com/user/repo.git
# Downloads a FULL copy of an existing repo, including its entire history

2 The daily loop: status, add, commit

This loop is the heartbeat of using Git. You'll run some version of this dozens of times a day:

git status
# Shows what changed: modified files, new (untracked) files, staged files

git add file.txt
git add .          # stage EVERYTHING changed in this folder — use carefully
git add -p         # interactively choose which CHUNKS of a file to stage

git commit -m "Fix login validation bug"
# Seals everything staged into a permanent snapshot with a message
💡 Write commit messages for your future self 6 months from now, not for right now. "fix bug" tells you nothing later. "Fix login validation rejecting valid emails with + symbol" does.

3 Looking at history

git log
# Full commit history: hash, author, date, message

git log --oneline --graph --all
# Compact, visual, shows branches — this is the one you'll actually use

git diff
# Shows exactly what changed, line by line, before you stage it

git diff --staged
# Shows what's staged and about to be committed

git show 
# Full detail of one specific commit

4 .gitignore — telling Git what to ignore

Not everything belongs in version control: build output, dependency folders (node_modules/), secrets, OS files like .DS_Store. A .gitignore file at your repo root lists patterns Git will never track.

# .gitignore
node_modules/
*.log
.env
dist/
.DS_Store
⚠️ Adding a pattern to .gitignore does NOT remove a file that's already tracked. If you accidentally committed a secret, you need git rm --cached plus rotating that secret — .gitignore only prevents FUTURE accidents.
