🔀 Merging & Conflicts Intermediate

Fast-forward vs three-way merges, reading conflict markers without panic, and getting unstuck with --abort.

1 Fast-forward merge: just move the pointer

If the branch you're merging in is directly ahead of your current branch — nothing new happened on your side — Git doesn't need a merge commit. It just slides your branch pointer forward. This is a fast-forward.

git switch main
git merge feature          # fast-forward if main hasn't moved

git merge --no-ff feature  # FORCE a merge commit even when FF is possible
# Many teams prefer --no-ff so the history records that a feature branch existed

2 Three-way merge: when both sides moved

If both branches have new commits since they split, Git performs a three-way merge: it compares your branch, their branch, and their common ancestor, then creates a new merge commit with two parents.

If the two branches changed different lines, Git merges them automatically and the merge commit is created with no fuss. If they changed the same lines, you get a conflict (next card).

3 Reading conflict markers

A conflict is not an error — it's Git saying "two people changed the same lines and I won't guess which to keep." Git edits the file in place, wrapping the clash in three markers:

<<<<<<< HEAD
color: blue;              # YOUR version (current branch)
=======
color: green;             # THEIR version (branch being merged)
>>>>>>> feature
  • Everything between <<<<<<< and ======= is your side (HEAD).
  • Everything between ======= and >>>>>>> is their side.
  • Edit the file to the version you want, delete all three marker lines, then stage and commit.
# After editing the file to the final, correct content:
git add style.css
git commit            # completes the merge (Git pre-fills a merge message)

4 Tools that make conflicts easier

git status
# Lists every file with "both modified" — your conflict to-do list

git merge --abort
# Panic button: throw away the half-done merge, return to the pre-merge state

git checkout --ours style.css     # keep YOUR whole version of this file
git checkout --theirs style.css   # keep THEIR whole version of this file

git mergetool
# Open a visual three-pane merge tool (VS Code, Beyond Compare, etc.)

git config --global merge.conflictstyle zdiff3
# Also show the common ANCESTOR in markers — far easier to reason about
💡 Turn on rerere ("reuse recorded resolution") with git config --global rerere.enabled true. Git remembers how you resolved a conflict and auto-applies the same resolution if the identical conflict appears again — a lifesaver on long-lived branches.

5 Merge vs rebase — the one-line answer

Merge preserves exactly what happened (two histories joined by a merge commit). Rebase rewrites your commits onto a new base for a clean, linear history. Merge is safe on shared branches; rebase is for tidying your own un-pushed work. The next page covers rebase in depth.

⚠️ There is no universally "correct" choice — it's a team convention. Pick one, write it down, and be consistent. The dangerous move is rebasing commits others have already pulled.
