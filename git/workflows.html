👥 Team Workflows Advanced

Git doesn't force a process on you — your team chooses one. The three common branching models, when each fits, and their trade-offs.

1 GitHub Flow — simple, continuous

One long-lived branch (main, always deployable). Every change is a short-lived feature branch off main, reviewed in a pull request, then merged and deployed. That's the whole model — ideal for web apps that ship many times a day.

💡 Best for: continuous deployment, small-to-mid teams, SaaS. Pros: dead simple, fast. Cons: no built-in notion of release versions — you rely on tags and CI to gate what reaches production.

2 Git Flow — structured releases

Two permanent branches: main (released code only) and develop (integration). Work happens on feature/* branches off develop; release/* branches stabilise a version; hotfix/* branches patch production directly off main.

⚠️ Best for: versioned software with scheduled releases, multiple versions in support (desktop apps, libraries). Cons: heavy — many branch types and merge directions. For continuously-deployed web apps it's usually overkill; the author himself now recommends simpler flows for those.

3 Trunk-Based Development — one trunk, tiny changes

Everyone commits to one shared trunk (main) at least daily, in very small increments, behind feature flags for anything unfinished. Branches, if used at all, live hours — not days. Relies heavily on strong CI and automated tests.

💡 Best for: high-velocity teams with excellent test coverage and CI (used at Google, Facebook-scale). Pros: minimal merge pain, continuous integration in the truest sense. Cons: demands discipline, feature flags, and fast, trustworthy automated checks.

4 Choosing — a quick guide

If your team…Use
Ships a web app continuously, small teamGitHub Flow
Has scheduled versioned releases & supports old versionsGit Flow
Has strong CI, wants true continuous integrationTrunk-Based
The common thread in all three: short-lived branches merge back often. The longer a branch lives apart from main, the more painful the eventual merge. Whatever model you pick, integrate frequently.
