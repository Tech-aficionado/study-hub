📈 GROUP BY & HAVING Intermediate

Collapsing many rows into per-group summaries, and the order the clauses actually run in.

1 The logical order of a SELECT

SQL is written SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT, but it executes in a different order. Knowing this explains almost every "why can't I use that alias / aggregate here" error.

💡 Because SELECT runs at step 5, a column alias you create there doesn't exist yet at WHERE (step 2) — but ORDER BY (step 6) can use it. And because HAVING runs after grouping, it can filter on aggregates while WHERE cannot.

2 GROUP BY basics

SELECT category_id, COUNT(*) AS n, ROUND(AVG(price), 2) AS avg_price
FROM products
GROUP BY category_id
ORDER BY n DESC;
🛑 The single-value rule: every column in the SELECT must either be in the GROUP BY or be inside an aggregate. PostgreSQL rejects a bare non-grouped column outright. MySQL historically allowed it (returning an arbitrary value) — modern MySQL blocks it under ONLY_FULL_GROUP_BY, which is on by default in 5.7+.

3 Grouping by multiple columns

SELECT country, status, COUNT(*) AS orders
FROM orders o
JOIN customers c ON c.id = o.customer_id
GROUP BY country, status
ORDER BY country, orders DESC;
-- One row per (country, status) combination that actually occurs

4 WHERE vs HAVING — before vs after

SELECT customer_id, COUNT(*) AS orders, SUM(1) AS n
FROM orders
WHERE status <> 'cancelled'      -- filter ROWS first (before grouping)
GROUP BY customer_id
HAVING COUNT(*) >= 4;             -- filter GROUPS after aggregation

5 DISTINCT vs GROUP BY

SELECT DISTINCT country FROM customers and SELECT country FROM customers GROUP BY country return the same rows. Reach for DISTINCT when you only want unique values; reach for GROUP BY when you also need an aggregate per group. COUNT(DISTINCT col) counts unique values within an aggregate.

SELECT COUNT(DISTINCT country) AS countries FROM customers;
