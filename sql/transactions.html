🔒 Transactions & Isolation Advanced

Grouping statements into all-or-nothing units, and the isolation levels that control what concurrent transactions can see.

1 ACID — the four guarantees

LetterGuarantee
AtomicityAll statements commit together or none do.
ConsistencyA transaction moves the DB from one valid state to another (constraints hold).
IsolationConcurrent transactions don't see each other's half-done work.
DurabilityOnce committed, it survives a crash (written to the WAL/redo log).

2 BEGIN / COMMIT / ROLLBACK

BEGIN;                                              -- start (START TRANSACTION in MySQL)
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                                             -- make it permanent
-- If anything went wrong before COMMIT:  ROLLBACK;  undoes the whole block
💡 The money-transfer example is the canonical case: debit and credit must both happen or both not. Without a transaction, a crash between the two UPDATEs loses $100 into thin air.
-- SAVEPOINT: a partial rollback point inside a transaction
BEGIN;
INSERT INTO orders ...;
SAVEPOINT after_order;
INSERT INTO order_items ...;     -- if this fails:
ROLLBACK TO after_order;         -- undo just the items, keep the order
COMMIT;

3 The concurrency anomalies isolation prevents

AnomalyWhat happens
Dirty readYou read another transaction's uncommitted change (which may be rolled back).
Non-repeatable readYou read a row twice in one transaction and get different values (someone committed an UPDATE in between).
Phantom readYou run the same query twice and new rows appear (someone committed an INSERT matching your WHERE).
Lost updateTwo transactions read-modify-write the same row; one overwrites the other's change.

5 Optimistic vs pessimistic locking

To prevent lost updates: pessimistic locks the row up front (SELECT … FOR UPDATE) so no one else can touch it. Optimistic adds a version column and only writes if the version is unchanged, retrying on conflict — better under low contention.

-- Pessimistic: lock the row for the rest of this transaction
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- Optimistic: only succeeds if nobody changed the version meanwhile
UPDATE accounts SET balance = 50, version = version + 1
WHERE id = 1 AND version = 7;   -- 0 rows updated → someone beat you → retry
