↕️ Sorting & Pagination Beginner

Ordering results and serving them one page at a time — including the trap that makes "page 500" slow.

1 ORDER BY

SELECT name, price FROM products ORDER BY price DESC;      -- high to low
SELECT * FROM customers ORDER BY country ASC, name ASC;   -- tie-break by name
SELECT * FROM products ORDER BY 2 DESC;                   -- by 2nd selected column (fragile — avoid)
⚠️ Without ORDER BY, row order is undefined — the engine may return rows in any order, and it can change between runs. Never rely on "natural" order; if you want an order, state it.

2 NULLs in sort order differ by dialect

DialectDefault NULL placementControl
PostgreSQLNULLs sort last in ASCORDER BY col NULLS FIRST / NULLS LAST
SQLiteNULLs sort first in ASCNULLS FIRST / LAST (3.30+)
MySQLNULLs sort first in ASCNo NULLS clause — use ORDER BY col IS NULL, col

3 LIMIT / OFFSET pagination

-- PostgreSQL / SQLite / MySQL
SELECT * FROM products ORDER BY id LIMIT 10;             -- page 1 (first 10)
SELECT * FROM products ORDER BY id LIMIT 10 OFFSET 20;   -- page 3 (skip 20, take 10)

-- SQL-standard spelling (PostgreSQL, SQL Server):
SELECT * FROM products ORDER BY id OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;
⚠️ Always pair pagination with a stable ORDER BY (e.g. a unique id). Without it, two different pages can return overlapping or missing rows because the underlying order isn't guaranteed.

4 Why OFFSET gets slow — and keyset pagination

OFFSET 100000 makes the database generate and then throw away 100,000 rows before returning the next page. Deep pages get progressively slower. Keyset (cursor) pagination fixes this by remembering the last row you saw and filtering past it.

-- First page
SELECT * FROM products ORDER BY id LIMIT 10;

-- Next page: pass the last id you saw (e.g. 10) — no OFFSET to skip past
SELECT * FROM products WHERE id > 10 ORDER BY id LIMIT 10;
