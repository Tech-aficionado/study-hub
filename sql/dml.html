✏️ INSERT, UPDATE, DELETE & UPSERT Beginner

Changing data safely — and the dialect-specific "insert or update" patterns.

1 INSERT — adding rows

-- one row
INSERT INTO customers (name, email) VALUES ('Ana', 'ana@example.com');

-- many rows in one statement (faster than many separate INSERTs)
INSERT INTO customers (name, email) VALUES
  ('Ben', 'ben@example.com'),
  ('Carla', 'carla@example.com');

-- insert the result of a query
INSERT INTO archived_orders (id, total)
SELECT id, total FROM orders WHERE order_date < '2020-01-01';
💡 Returning the new id: PostgreSQL & SQLite support INSERT … RETURNING id;. MySQL uses LAST_INSERT_ID() after the insert.

2 UPDATE — changing existing rows

UPDATE products
SET price = price * 1.10          -- 10% price rise
WHERE category_id = 1;

-- update using a value from another table (PostgreSQL)
UPDATE orders o
SET status = 'vip'
FROM customers c
WHERE c.id = o.customer_id AND c.country = 'US';
🛑 An UPDATE with no WHERE touches EVERY row. Preview with a SELECT using the same WHERE first, and run inside a transaction so you can ROLLBACK a mistake.

3 DELETE — removing rows

DELETE FROM orders WHERE status = 'cancelled';

-- empty a whole table fast (resets, no per-row triggers/undo granularity)
TRUNCATE TABLE sessions;    -- PostgreSQL / MySQL; SQLite uses DELETE FROM sessions;

4 UPSERT — insert, or update if it already exists

"Insert this row; if a row with the same key already exists, update it instead." The syntax is one of the biggest dialect differences in all of SQL.

-- PostgreSQL & SQLite: ON CONFLICT
INSERT INTO customers (email, name) VALUES ('ana@example.com', 'Ana B.')
ON CONFLICT (email)
DO UPDATE SET name = EXCLUDED.name;   -- EXCLUDED = the row we tried to insert

-- MySQL: ON DUPLICATE KEY UPDATE
INSERT INTO customers (email, name) VALUES ('ana@example.com', 'Ana B.')
ON DUPLICATE KEY UPDATE name = VALUES(name);
-- MySQL 8.0.19+: ... AS new ON DUPLICATE KEY UPDATE name = new.name;
⚠️ UPSERT needs a UNIQUE or PRIMARY KEY constraint to detect the "conflict" — ON CONFLICT (email) only works if email is UNIQUE. Without a unique key there is nothing to conflict on.

5 Soft deletes — a common real-world pattern

Many apps never physically DELETE user data; they set a deleted_at timestamp and filter it out. This preserves history, enables "undo," and keeps foreign keys intact.

UPDATE users SET deleted_at = now() WHERE id = 42;   -- "delete"
SELECT * FROM users WHERE deleted_at IS NULL;         -- "live" rows only
