⚡ Indexes, Transactions & Views Advanced

The tools that make queries fast and keep multi-step operations safe.

1 Indexes — why some queries are instant and others crawl

Without an index, finding a row means scanning EVERY row in the table (a "full table scan") — fine for 100 rows, catastrophic for 100 million. An index is a separate, sorted data structure (usually a B-tree) that lets the database jump straight to matching rows, similar to a book's index pointing you to the right page instead of reading cover to cover.

CREATE INDEX idx_orders_user_id ON orders(user_id);
-- Speeds up: WHERE user_id = ... and JOIN ... ON orders.user_id = ...

EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;
-- Shows the actual execution plan — reveals whether an index was used
⚠️ Indexes aren't free — they speed up reads but slow down writes (every INSERT/UPDATE must also update the index) and take disk space. Index columns you actually filter/join on, not every column reflexively.

2 Transactions and ACID

A transaction groups multiple statements so they succeed or fail as ONE unit — critical for "transfer $100 from account A to B," which is really two writes that must both happen or both not happen.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- If anything fails between BEGIN and COMMIT, run ROLLBACK instead to undo everything
ACID letterGuarantee
AtomicityAll statements in the transaction succeed, or none do
ConsistencyThe database never ends up in an invalid state
IsolationConcurrent transactions don't see each other's half-finished work
DurabilityOnce committed, data survives even a crash immediately after

3 Views — a saved query that looks like a table

CREATE VIEW active_customers AS
SELECT * FROM users WHERE deleted_at IS NULL AND last_login > NOW() - INTERVAL '30 days';

SELECT * FROM active_customers WHERE country = 'US';
-- Query the view just like a normal table — it re-runs the underlying query each time
💡 Views are great for hiding complexity (a messy multi-join query becomes a simple SELECT) and for access control (grant permission on a view that excludes sensitive columns, not the raw table).

4 Window functions — aggregates without collapsing rows

SELECT id, user_id, total,
  RANK() OVER (ORDER BY total DESC) AS rank_overall,
  AVG(total) OVER (PARTITION BY user_id) AS avg_for_this_user
FROM orders;
-- Unlike GROUP BY, every original row still appears — you get the aggregate
-- ALONGSIDE the row's own data, not instead of it
