💾 Databases & DBMS Beginner

What a database actually is, what the software around it does, and where relational SQL sits among the alternatives.

1 Database vs DBMS vs SQL — three different things

People use "database" loosely, but three distinct ideas hide inside the word:

  • A database is the actual collection of data — your tables, rows, and the file(s) on disk that hold them.
  • A DBMS (Database Management System) is the software that stores, protects, and serves that data — PostgreSQL, MySQL, SQLite, SQL Server, Oracle. It handles concurrency, crash recovery, access control, and query optimisation so you don't have to.
  • SQL is the language you use to talk to a relational DBMS. The DBMS is the engine; SQL is how you give it instructions.
💡 Analogy: the database is the warehouse of goods, the DBMS is the warehouse staff and systems (security, forklifts, inventory logs), and SQL is the order form you fill out to say "send me 10 of item X."

2 What a DBMS does for you (so you don't rebuild it)

JobWhy it matters
Durability & crash recoveryCommitted data survives a power cut — the DBMS uses a write-ahead log to replay or roll back on restart.
Concurrency controlThousands of users read/write at once without corrupting each other's data (locks, MVCC).
Query optimisationYou say what you want; the planner decides the fastest how (which index, join order).
Integrity enforcementConstraints (keys, CHECK, NOT NULL) stop invalid data at the door.
Access controlGRANT/REVOKE decide who can read or change what.

3 The relational model — tables, rows, columns, keys

A relational database organises data into relations (tables). Each table has a fixed set of columns (attributes, each with a type) and any number of rows (records). Tables connect through keys: a primary key uniquely names each row, a foreign key in one table points at a primary key in another.

4 Relational vs NoSQL — not better, different

"NoSQL" is an umbrella for databases that drop the strict relational table model for a different shape. The honest framing is trade-offs, not winners.

DimensionRelational (SQL)NoSQL (document/key-value/column/graph)
Data shapeFixed schema of typed columnsFlexible — JSON documents, key-value pairs, graphs
RelationshipsJoins across normalised tablesOften embedded/duplicated; joins limited or absent
TransactionsStrong ACID across many rows/tablesOften per-document; varies widely by product
ScalingScales up well; sharding is extra workMany are built to scale out across many nodes
Best forStructured data with relationships & integrity (orders, finance, inventory)Rapidly changing/semi-structured data, huge scale, caching, graphs
Examples: Document — MongoDB, Couchbase. Key-value — Redis, DynamoDB. Wide-column — Cassandra, HBase. Graph — Neo4j. Many apps use a relational database as the source of truth and a NoSQL store (e.g. Redis) alongside it for caching.
⚠️ "NoSQL" originally meant "non-relational," not "no SQL at all." Many NoSQL engines now offer SQL-like query languages, and relational databases (PostgreSQL, MySQL) store and query JSON natively — the line is blurrier than the marketing suggests.

5 OLTP vs OLAP — two jobs, two shapes

The same relational model serves two very different workloads:

  • OLTP (Online Transaction Processing) — many small, fast reads and writes: "place this order," "update this balance." Normalised schemas, row-oriented storage. This is what most of this course targets.
  • OLAP (Online Analytical Processing) — few huge aggregating queries over history: "revenue by region by quarter." Often denormalised star schemas and column-oriented engines (BigQuery, Snowflake, DuckDB, ClickHouse).
