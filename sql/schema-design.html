🏗️ Schema Design Intermediate

Primary keys, foreign keys, and normalization — designing tables that don't contradict themselves.

1 Primary and foreign keys

A primary key uniquely identifies each row in a table (usually an auto-incrementing id). A foreign key is a column in one table that references a primary key in another — this is literally what makes a database "relational."

CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  user_id INTEGER REFERENCES users(id),
  total NUMERIC(10,2)
);
⚠️ A foreign key constraint PREVENTS inserting an order with a user_id that doesn't exist in users — the database enforces this automatically, catching bugs that would otherwise create "orphan" rows.

2 Normalization — why not just put everything in one giant table

Normalization is the process of splitting data to avoid storing the same fact in multiple places, which prevents data from contradicting itself.

FormRule
1NFEach column holds one atomic value — no comma-separated lists in a single cell
2NFEvery non-key column depends on the WHOLE primary key, not just part of it
3NFNo column depends on another NON-key column (no transitive dependency)
Example of the problem normalization solves: if a customer's address is stored in every single order row, updating their address means updating 50 rows — miss one, and now your data disagrees with itself.

3 When to deliberately break normalization

Sometimes a denormalized design (duplicating some data) is a deliberate tradeoff for read performance — e.g. storing a cached order_count on the users table instead of counting orders every time. This trades write complexity for read speed, and should be a conscious choice, not an accident.
