🛡️ SQL Injection & Safe Queries Advanced

The most common database vulnerability — and the one-line habit that eliminates it.

1 What SQL injection is

SQL injection happens when user input is concatenated into a query string, letting an attacker's text become executable SQL instead of data. It's consistently near the top of the OWASP Top 10.

# VULNERABLE — never build SQL by string formatting
query = "SELECT * FROM users WHERE email = '" + user_input + "'"

# If user_input is:   ' OR '1'='1
# the query becomes:  SELECT * FROM users WHERE email = '' OR '1'='1'
# → '1'='1' is always true → returns EVERY user
🛑 Beyond reading all rows, injection can run ; DROP TABLE users; --, exfiltrate data via UNION, or bypass logins. The classic xkcd "Bobby Tables" joke is exactly this: a student named Robert'); DROP TABLE Students;--.

2 The fix: parameterised queries

Send the SQL and the values separately. The driver sends the query structure to the database first, then binds values as pure data — they can never be reinterpreted as SQL. This is the single most important security habit in all of database programming.

3 Python — the right way

# SQLite (sqlite3) — ? placeholders
import sqlite3
conn = sqlite3.connect("shop.db")
cur = conn.cursor()
cur.execute("SELECT * FROM users WHERE email = ?", (user_input,))
rows = cur.fetchall()

# PostgreSQL (psycopg) — %s placeholders (NOT Python string formatting!)
import psycopg
with psycopg.connect("dbname=shop") as conn:
    cur = conn.execute("SELECT * FROM users WHERE email = %s", (user_input,))
    rows = cur.fetchall()
🛑 %s here is a driver placeholder, not Python's % operator. NEVER do cur.execute("… WHERE email = '%s'" % user_input) — that's string formatting, which is exactly the vulnerability. Pass values as the second argument.

4 Node.js — the right way

// node-postgres (pg) — $1, $2 placeholders
const { Pool } = require('pg');
const pool = new Pool();
const { rows } = await pool.query(
  'SELECT * FROM users WHERE email = $1',
  [userInput]            // values array — bound safely by the driver
);

// mysql2 — ? placeholders
const mysql = require('mysql2/promise');
const conn = await mysql.createConnection({ /* ... */ });
const [rows] = await conn.execute(
  'SELECT * FROM users WHERE email = ?',
  [userInput]
);

// better-sqlite3 — ? placeholders, prepared statement
const db = require('better-sqlite3')('shop.db');
const row = db.prepare('SELECT * FROM users WHERE email = ?').get(userInput);
⚠️ Template literals are a trap in JS: pool.query(`… WHERE email = '${userInput}'`) is string interpolation — just as vulnerable as concatenation. Use $1/? placeholders with a values array.

5 What placeholders can't parameterise, and defence in depth

Placeholders bind values, not identifiers. You cannot parameterise a table name, column name, or ORDER BY direction. For those, allow-list against known-safe values:

# sort column must be one you explicitly permit — never raw user input
ALLOWED = {"name", "price", "created_at"}
col = user_sort if user_sort in ALLOWED else "name"
cur.execute(f"SELECT * FROM products ORDER BY {col}")   # safe: col is from the allow-list
  • Use an ORM/query builder (SQLAlchemy, Prisma, Knex) — they parameterise by default.
  • Least privilege — the app's DB user shouldn't have DROP/GRANT rights.
  • Validate & constrain input types/lengths as a second layer, but parameterisation is the real fix — not input "sanitising" by escaping quotes yourself.
