🪟 Window Functions Advanced

Aggregate-style calculations that keep every row — rankings, running totals, and row-to-row comparisons.

1 The key idea: aggregate without collapsing

GROUP BY turns many rows into one per group. A window function computes a value across a set of rows but returns it alongside every original row — nothing collapses.

SELECT name, department_id, salary,
  AVG(salary) OVER (PARTITION BY department_id) AS dept_avg
FROM employees;
-- Every employee row kept, with their department's average salary attached

2 OVER, PARTITION BY, ORDER BY

  • OVER (…) — marks a function as a window function and defines the window.
  • PARTITION BY — splits rows into groups the window resets for (like GROUP BY, but non-collapsing). Omit it to treat all rows as one partition.
  • ORDER BY (inside OVER) — orders rows within each partition; required for ranking and running totals.

3 Ranking: ROW_NUMBER, RANK, DENSE_RANK

SELECT name, salary,
  ROW_NUMBER() OVER (ORDER BY salary DESC) AS row_num,
  RANK()       OVER (ORDER BY salary DESC) AS rnk,
  DENSE_RANK() OVER (ORDER BY salary DESC) AS dense
FROM employees;

💡 On ties: ROW_NUMBER always gives distinct numbers (arbitrary tie-break), RANK gives ties the same rank then skips (1,1,3), DENSE_RANK gives ties the same rank with no gap (1,1,2). "Nth highest salary" interview questions hinge on this difference.

4 Top-N-per-group — the canonical pattern

WITH ranked AS (
  SELECT name, department_id, salary,
    ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rn
  FROM employees
)
SELECT * FROM ranked WHERE rn <= 3;   -- top 3 earners in EACH department

You can't filter on a window function directly in WHERE (windows run after WHERE), so wrap it in a CTE/subquery and filter the computed rank there.

5 LAG and LEAD — look at neighbouring rows

SELECT order_date, daily_total,
  LAG(daily_total)  OVER (ORDER BY order_date) AS prev_day,
  daily_total - LAG(daily_total) OVER (ORDER BY order_date) AS change,
  LEAD(daily_total) OVER (ORDER BY order_date) AS next_day
FROM daily_sales;
-- LAG = previous row's value, LEAD = next row's — perfect for period-over-period deltas
💡 "Consecutive days / increasing values" interview problems (e.g. LeetCode Rising Temperature, Consecutive Numbers) are naturally solved with LAG comparing each row to the one before.

6 Running totals and frames

SELECT order_date, amount,
  SUM(amount) OVER (ORDER BY order_date
                    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
  AVG(amount) OVER (ORDER BY order_date
                    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS moving_avg_3
FROM sales;

The frame clause (ROWS/RANGE BETWEEN … AND …) defines which rows the function sees relative to the current row. UNBOUNDED PRECEDING … CURRENT ROW is a running total; 2 PRECEDING … CURRENT ROW is a 3-row moving window.

⚠️ When you add ORDER BY to an aggregate window with no explicit frame, the default frame is RANGE UNBOUNDED PRECEDING TO CURRENT ROW — which already gives a running total, but RANGE treats ties as one group. Use ROWS for a strict row-by-row window.
💡 Other useful window functions: NTILE(4) (quartiles/buckets), FIRST_VALUE/LAST_VALUE, NTH_VALUE, and PERCENT_RANK/CUME_DIST for distributions. All supported in PostgreSQL, modern MySQL (8.0+), and SQLite (3.25+).
