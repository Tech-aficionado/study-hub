🗂️ Views, Procedures & Triggers Advanced

Reusable logic that lives inside the database — saved queries, callable routines, and automatic reactions to data changes.

1 Views — a saved query that looks like a table

CREATE VIEW active_customers AS
SELECT id, name, email FROM customers WHERE deleted_at IS NULL;

SELECT * FROM active_customers WHERE email LIKE '%@gmail.com';
-- Query the view like a table — it re-runs the underlying SELECT each time
💡 Views shine for two things: hiding complexity (a messy 5-table join becomes SELECT * FROM report) and access control (grant SELECT on a view that excludes the salary column instead of the raw table).

2 Materialized views — cached results

A regular view re-computes every query. A materialized view stores the result on disk and you refresh it on a schedule — great for expensive analytics that don't need to be real-time.

-- PostgreSQL
CREATE MATERIALIZED VIEW monthly_revenue AS
SELECT date_trunc('month', order_date) AS month, SUM(total) AS revenue
FROM orders GROUP BY 1;

REFRESH MATERIALIZED VIEW monthly_revenue;   -- recompute when you want fresh data
⚠️ PostgreSQL and Oracle have native materialized views. MySQL does not — you emulate them with a real table plus a scheduled job/trigger. SQLite has no materialized views either.

3 Stored procedures and functions

Routines that live in the database and run close to the data — useful for multi-step logic, batch jobs, and enforcing rules centrally.

-- PostgreSQL function
CREATE OR REPLACE FUNCTION order_total(p_order_id INT)
RETURNS NUMERIC AS $$
  SELECT SUM(quantity * unit_price)
  FROM order_items WHERE order_id = p_order_id;
$$ LANGUAGE sql;

SELECT order_total(10);
DialectProcedural language
PostgreSQLPL/pgSQL (and others), CREATE FUNCTION / CREATE PROCEDURE
MySQLCREATE PROCEDURE … BEGIN … END with a changed DELIMITER
SQLiteNo stored procedures — do it in application code

4 Triggers — automatic reactions to changes

A trigger runs a block of SQL automatically when a row is inserted, updated, or deleted. Common uses: audit logs, maintaining denormalized counts, enforcing complex rules, setting updated_at.

-- SQLite: write an audit row whenever a product's price changes
CREATE TRIGGER log_price_change
AFTER UPDATE OF price ON products
FOR EACH ROW
BEGIN
  INSERT INTO price_log (product_id, old_price, new_price, changed_at)
  VALUES (OLD.id, OLD.price, NEW.price, datetime('now'));
END;

OLD and NEW reference the row before and after the change. Triggers fire BEFORE or AFTER the operation.

🛑 Triggers are powerful but invisible — logic that fires with no call site in your app code is hard to debug and easy to forget. Use them for cross-cutting concerns (auditing), not core business logic that belongs in reviewable application code.

5 When to push logic into the database vs the app

  • In the DB: integrity rules every client must obey, auditing, performance-critical set operations, and logic shared by many apps.
  • In the app: business rules that change often, anything needing tests/version control/code review, and logic you want portable across database engines.
