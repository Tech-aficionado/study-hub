📊 Aggregation & Subqueries Intermediate

Turning many rows into summary numbers, and queries nested inside other queries.

1 Aggregate functions

SELECT COUNT(*) FROM orders;                 -- how many rows total
SELECT SUM(total) FROM orders;                -- add up a column
SELECT AVG(total) FROM orders;                -- average value
SELECT MIN(total), MAX(total) FROM orders;    -- smallest / largest

2 GROUP BY — aggregating per category

Without GROUP BY, an aggregate collapses the WHOLE table into one number. GROUP BY computes that aggregate separately FOR EACH distinct value in a column.

SELECT user_id, COUNT(*) AS order_count
FROM orders
GROUP BY user_id;
-- One row per user, showing how many orders EACH of them placed

SELECT category, AVG(price) AS avg_price
FROM products
GROUP BY category
ORDER BY avg_price DESC;

3 HAVING — filtering AFTER grouping

WHERE filters individual rows BEFORE grouping happens. HAVING filters the GROUPS themselves, after aggregation — this is why you can't put an aggregate function inside WHERE.

SELECT user_id, COUNT(*) AS order_count
FROM orders
GROUP BY user_id
HAVING COUNT(*) > 5;
-- Only users with MORE THAN 5 orders — this is impossible to express with WHERE

4 Subqueries — a query inside a query

SELECT name FROM users
WHERE id IN (
  SELECT user_id FROM orders WHERE total > 1000
);
-- The inner query runs first, producing a list of user_ids,
-- the outer query then finds users matching that list

SELECT name, (
  SELECT COUNT(*) FROM orders WHERE orders.user_id = users.id
) AS order_count
FROM users;
-- A "correlated" subquery — runs once PER outer row, referencing it
💡 A correlated subquery can be slow on large tables because it re-runs for every outer row. A JOIN with GROUP BY often achieves the same result faster — worth comparing both when performance matters.
