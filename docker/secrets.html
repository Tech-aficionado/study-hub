🔐 Environment Variables & Secrets Intermediate

How to configure a container from the outside — and the critical line between harmless config and a leaked password.

1 Why configure from outside the image?

The same image should run in dev, staging and production without rebuilding. The way you make one image behave differently in each place is to pass configuration at run time rather than hard-coding it. The main lever is the environment variable.

Good config to pass this way: the port to listen on, the log level, a feature flag, the URL of a dependency. The app reads these from its environment and adapts.

2 Setting environment variables

# one at a time
docker run -e LOG_LEVEL=debug -e PORT=8080 myapp

# from a file (one KEY=value per line) — keeps secrets out of shell history
docker run --env-file ./app.env myapp

# a baked-in default in the Dockerfile (overridable at run time)
ENV PORT=8080

In Compose you list them under a service's environment:, or point to an env_file:. Compose also does ${VAR} interpolation from a local .env file, so you can parametrise the compose file itself.

docker run -e / Compose environmentHighest — overrides everything
--env-file / env_fileMiddle

3 The trap: ENV and ARG are NOT for secrets

It's tempting to pass a database password or API token as an environment variable or a build ARG. Don't. Here's why each leaks:

  • ARG / ENV in a Dockerfile are stored in the image's layer history — anyone with the image can run docker history and read them.
  • Runtime -e env vars are visible in docker inspect, in the container's /proc, and routinely get dumped into logs and crash reports.
🚫 A password in ENV DB_PASSWORD=… is baked into the image forever — even if you "remove" it in a later layer, the earlier layer still contains it. Never put a secret in a Dockerfile.

4 Build-time secrets, done right

If a build genuinely needs a credential (a private npm token, an SSH key to clone a repo), use BuildKit's secret mount. It makes the value available to a single RUN step and never writes it into a layer.

# Dockerfile
RUN --mount=type=secret,id=npmtoken \
    NPM_TOKEN=$(cat /run/secrets/npmtoken) npm ci
# build — the file is passed in but never baked in
docker build --secret id=npmtoken,src=./npm_token.txt -t myapp .

5 Runtime secrets

For secrets a running container needs, deliver them as mounted files, not env vars. Compose and Swarm have first-class secrets: that appear under /run/secrets/ inside the container; the app reads the file. In the cloud, an external manager (Vault, AWS/GCP secret stores) injects them the same way.

# compose.yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
secrets:
  db_password:
    file: ./db_password.txt
💡 Notice the pattern: official images increasingly accept a *_FILE variant (POSTGRES_PASSWORD_FILE) precisely so you can hand them a file path instead of putting the secret in a plain env var.
⚠️ And always add secret files (*.env, db_password.txt) to .gitignore and .dockerignore so they never reach a repo or a build context.
