🪟 Desktop vs Engine & Windows/WSL2 Intermediate

What you're actually installing, and the Linux kernel hiding under Docker on a Mac or Windows PC.

1 Containers need a Linux kernel

The single fact that explains everything on this page: Linux containers are built from Linux kernel features — namespaces and cgroups. There is no such thing as a container without a kernel to isolate against. On a Linux server that kernel is right there. On a Mac or a Windows PC it isn't — so Docker quietly runs a small Linux virtual machine and puts the containers inside that.

💡 When you run docker run ubuntu on your Mac, "ubuntu" isn't running on macOS — it's running on a lightweight Linux VM that Docker manages for you, and the CLI on your Mac just talks to it.

In short: Desktop is Engine plus a friendly box around it and the plumbing to run on a non-Linux OS. On a Linux server you usually just install Engine.

3 WSL2 — the Linux backend on Windows

On Windows, the Linux VM is provided by WSL2 (Windows Subsystem for Linux, version 2). WSL2 runs a real Linux kernel in a lightweight, tightly-integrated VM. Docker Desktop installs its daemon into WSL2, and the Windows docker CLI talks to it. You also get Docker automatically available inside your WSL2 Linux distros (Ubuntu, etc.).

Why WSL2 and not the older Hyper-V backend: it starts faster, uses memory dynamically (gives RAM back when idle), and has far better filesystem performance for files kept inside the Linux side.

4 The #1 Windows performance gotcha: where your files live

WSL2 has two filesystems, and crossing between them is slow. Your Windows drive (C:\Users\you\project) is reachable from Linux as /mnt/c/Users/you/project, but that path crosses the Windows↔Linux boundary on every file access. A bind-mounted project there — especially with node_modules or hot-reload — can be painfully slow.

⚠️ Keep your code inside the WSL2 filesystem (e.g. \\wsl$\Ubuntu\home\you\project or just work from the Linux home dir). Bind mounts and file-watching there run at native Linux speed. Editing from /mnt/c is the usual cause of "Docker on Windows is so slow".
# in a WSL2 terminal — fast
cd ~/projects/myapp          # lives in the Linux filesystem
docker compose up

# slow: project under /mnt/c/... bind-mounted into a container

5 Windows containers vs Linux containers

One more wrinkle: Docker Desktop on Windows can also run native Windows containers (which share the Windows kernel and run Windows binaries), switched via "Switch to Windows containers". These are a separate world from Linux containers — a Linux image won't run as a Windows container and vice-versa. The overwhelming majority of images (and everything else in this course) are Linux containers; reach for Windows containers only when you must run a Windows-only app like a .NET Framework service.

💡 Rule of thumb: unless you specifically need Windows binaries, stay in Linux-container mode — it's the default and where the whole ecosystem lives.
