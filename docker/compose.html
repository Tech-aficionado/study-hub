🧩 Docker Compose Intermediate

Describe your whole stack once, start it with one command.

1 The problem Compose solves

A real app is rarely just one container. It's usually a web server, a backend API, a database, maybe a cache — several containers that all need to start together, in the right order, wired to the same network. Running each one by hand with a long docker run command, every single time, gets old fast and is easy to get wrong.

Docker Compose lets you write the whole stack down once, in one YAML file, and then bring the entire thing up — or tear it entirely down — with a single command. It also quietly creates a shared network for all those services, so they can already reach each other by name with zero extra setup. It's basically "infrastructure as code" for your local stack: the file can be committed to Git, so anyone on the team gets the exact same setup by running one command.

2 Reading a real example, piece by piece

Here's a typical stack: a web app, a Postgres database, and a Redis cache. Walking through it: services lists every container you want; each service's ports opens a door from your machine into that container; volumes keeps the database's data safe even if the container is destroyed; and depends_on tells Compose "start the database before the web app."

# docker-compose.yml
services:
  web:
    build: .
    ports:
      - "3000:3000"
    environment:
      - DATABASE_URL=postgres://db:5432/app
    depends_on:
      - db
    volumes:
      - ./src:/app/src          # live reload in dev

  db:
    image: postgres:16-alpine
    environment:
      - POSTGRES_PASSWORD=secret
    volumes:
      - dbdata:/var/lib/postgresql/data

  redis:
    image: redis:7-alpine

volumes:
  dbdata:

3 The handful of commands you'll actually use

docker compose up -d          # start everything, in the background
docker compose ps             # what's running right now?
docker compose logs -f web    # follow one service's logs live
docker compose exec web bash  # open a shell inside a running service
docker compose build          # rebuild images after a Dockerfile change
docker compose down           # stop and remove everything Compose created
docker compose down -v        # same, but also wipe the volumes/data
docker compose config         # sanity-check the file, print the resolved config
💡 depends_on only controls the START ORDER — it does not wait for the database to be actually ready to accept connections. If your app crashes on startup because the DB isn't ready yet, add a healthcheck plus condition: service_healthy.
