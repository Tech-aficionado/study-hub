📦 Images & Layers Beginner

How Docker images are built from stacked, cached layers.

1 Image vs container, finally explained clearly

If you've coded before, this click instantly: an image is like a class, and a container is like an object made from that class. The image is the inert, unchanging template sitting in storage. A container is what you get the moment you actually run that image — it's alive, it has a process, it can be stopped and started.

There's also a classic physical analogy worth knowing: a Docker container is named after real shipping containers. A shipping container can hold anything — furniture, electronics, food — but every ship, crane, and truck in the world handles it the exact same standard way. Swap the contents (Node.js app, Postgres database, Redis cache) and the "shipping" mechanism (the Docker runtime) doesn't care — it loads and runs it the same way on any server, OS, or cloud.

Under the hood, every instruction in your Dockerfile — RUN, COPY, ADD — stacks one more read-only layer onto the image. When you finally run it as a container, Docker adds one last thin layer on top that you're actually allowed to write to.

These layers are cached and shared across images. If two different images both start with FROM python:3.12-slim, that layer is only ever stored once on your disk and only ever downloaded once — not twice.

2 Essential image commands

docker pull nginx:latest        # download an image
docker images                  # list local images
docker build -t myapp:1.0 .    # build from Dockerfile
docker tag myapp:1.0 myapp:latest
docker rmi myapp:1.0           # remove an image
docker history myapp:1.0       # inspect layers
docker inspect myapp:1.0       # full metadata as JSON

3 Image tags: don't let "latest" fool you

An image name follows the shape [registry/]repository[:tag]. If you leave the tag off, Docker quietly assumes :latest — but despite the name, that is not guaranteed to mean "the newest stable version." It's just whatever label happened to be pushed last.

⚠️ Never rely on :latest in anything real — it means two people running "the same" build command on different days can silently get different code. Pin an exact version instead, like python:3.12.4-slim, not python:latest.
