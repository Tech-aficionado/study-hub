🔎 Logging & Debugging Containers Intermediate

When a container misbehaves, these are the commands and the mental model that find the cause fast.

1 The golden rule: log to stdout, not to files

Docker captures whatever a container's main process writes to stdout and stderr. That's the one stream it knows about, and docker logs replays it. If your app writes to a log file inside the container instead, Docker can't see it, docker logs shows nothing, and the file dies with the container.

So the container convention — unlike a traditional server — is: send logs to stdout/stderr and let the platform collect them. Most official images already do this.

💡 "Empty docker logs" almost always means the app is logging to a file, not that nothing happened. Point its logging at stdout.

2 Reading logs

docker logs web                 # everything collected so far
docker logs -f web              # follow — stream new lines live (like tail -f)
docker logs --tail 100 web      # just the last 100 lines
docker logs --since 10m web     # only the last 10 minutes
docker logs -t web              # prepend timestamps

Combine them: docker logs -f --tail 50 web is the everyday "show me recent output and keep streaming" command.

3 Logging drivers — where the logs actually go

How Docker stores or forwards those streams is set by the logging driver. The default keeps JSON files on the host; others ship logs straight to a central system.

DriverUse for
json-file (default)Local JSON files; supports docker logs. Set rotation or it grows forever.
localEfficient on-disk format with rotation built in
journald / syslogHand off to the host's logging system
fluentd / gelf / awslogs / splunkCentralised log aggregation
# cap json-file size so logs can't fill the disk
docker run -d --log-driver json-file \
  --log-opt max-size=10m --log-opt max-file=3 nginx
⚠️ The default json-file driver has no rotation out of the box. A chatty container can quietly eat an entire disk over days. Set max-size/max-file per container, or globally in /etc/docker/daemon.json.

4 Debugging a running container from the inside

When logs aren't enough, step inside with exec — it runs a new process in an already-running container (it fails on a stopped one).

docker exec -it web sh          # interactive shell (sh; use bash if present)
docker exec web env             # dump environment variables
docker exec web ps aux          # what's actually running inside
docker exec web cat /etc/hosts  # inspect config without a shell

docker top web                  # process table from the host side
docker stats web                # live CPU / memory / I/O
docker port web                 # which ports are published
docker diff web                 # files changed vs the image

If the image is minimal (distroless/scratch) there's no shell to exec into. Modern Docker offers docker debug <container> (Desktop) which attaches a toolbox even to those; otherwise copy a static busybox in, or reproduce with a fatter base image.

5 Debugging a container that won't stay up

If a container exits immediately, docker logs may be nearly empty. Work the exit code and events:

docker ps -a                    # read the exit code in STATUS
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.Error}}' web
docker events                   # live stream of daemon events (die, oom, kill)
Exit codeUsually means
0Process finished normally — if it restarts, your CMD is a one-shot command, not a long-running server
137SIGKILL — frequently an out-of-memory kill (check OOMKilled: true, raise --memory)
139Segfault (SIGSEGV) inside the app
143SIGTERM — stopped gracefully
🚫 A classic trap: the app logs to a file, so docker logs is empty, and you chase a "silent crash" that is really a non-zero exit visible in docker ps -a all along. Read the exit code first.
