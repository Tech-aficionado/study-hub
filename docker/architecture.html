🏗️ Docker Architecture Beginner

Client, daemon, and the pieces that work together.

1 Client–Server model

When you type a docker command, you're not talking to Docker directly — you're talking to a small client program that forwards your request over an API to the real worker: the Docker daemon (dockerd), running quietly in the background. The daemon is what actually builds images, starts containers, and manages everything. They don't even have to be on the same machine — that's how you can control a Docker setup on a remote server from your own laptop.

2 The six things you'll keep hearing about

ComponentIn plain words
ImageA frozen template — code + dependencies + settings. Nothing is running yet.
ContainerAn image that's actually been started — a living, running (or stopped) instance.
DockerfileThe recipe/instructions used to build an image in the first place.
RegistryWhere images are stored so others can download them (Docker Hub, ECR, GHCR).
VolumeStorage that survives even after the container that used it is deleted.
NetworkThe virtual wiring that lets containers reach each other and the outside world.

3 What makes this possible under the hood

You don't need to memorize these, but it helps to know Docker isn't magic — it's built from real Linux kernel features that already existed:

  • Namespaces — control what a process can SEE. Give a container its own namespace and it thinks it's the only thing running on the machine (its own process list, its own network interface, its own hostname).
  • Control Groups (cgroups) — control what a process can USE. This is how you can cap a container at, say, 512MB of RAM or half a CPU core.
  • Union filesystems (OverlayFS) — the trick that lets Docker stack several read-only layers and place one writable layer on top, without copying everything each time.
On Windows or Mac, there's no Linux kernel to share directly — so Docker Desktop quietly runs a small Linux VM behind the scenes. That's why it uses some RAM even when you're not running any containers.
