📝 Writing Dockerfiles Intermediate

The recipe that builds your image.

1 What a Dockerfile actually is

A Dockerfile is just a plain text file with a short list of steps, read top to bottom: "start from this base, copy in these files, run this install command, and when someone starts the container, run this." Docker reads it and builds an image out of it — one that you can then start as a container as many times as you like.

# 1. Base image to build from
FROM node:20-alpine

# 2. Metadata (optional)
LABEL maintainer="you@example.com"

# 3. Set working directory inside the image
WORKDIR /app

# 4. Copy dependency manifests FIRST (layer caching!)
COPY package*.json ./
RUN npm ci --omit=dev

# 5. Copy the rest of the source
COPY . .

# 6. Document the port the app listens on
EXPOSE 3000

# 7. Run as non-root user (security)
USER node

# 8. The command that runs when the container starts
CMD ["node", "server.js"]
💡 Each instruction is cached, and the ones that change files (RUN, COPY, ADD) each add a filesystem layer. When something changes, Docker rebuilds from that step downward and reuses everything above it from cache. Edit your source code and only step 5 onward reruns — the slow npm ci in step 4 is reused, because package.json didn't change. That's why the order of your Dockerfile matters for build speed.

2 Key instructions reference

InstructionPurpose
FROMBase image — always the first instruction
RUNExecute a command at BUILD time, creates a new layer
COPYCopy files from build context into the image
ADDLike COPY, but also extracts tar files & fetches URLs
WORKDIRSet the working directory for subsequent instructions
ENVSet environment variable, persists into running container
EXPOSEDocument which port the app uses
CMDDefault command when container starts (overridable)
ENTRYPOINTFixed executable; CMD becomes its args
USERSwitch to a non-root user
ARGBuild-time-only variable
VOLUMECreate a mount point for persistent storage
HEALTHCHECKPeriodic container health check

3 CMD vs ENTRYPOINT — the one thing that trips everyone up

Both say "run this when the container starts," but they behave differently if someone tries to override it when running the container.

CMD alone — fully replaceable:

CMD ["python", "app.py"]
# docker run myimg → runs python app.py
# docker run myimg bash → runs bash INSTEAD, the whole CMD is thrown away

ENTRYPOINT + CMD — CMD just becomes a default argument:

ENTRYPOINT ["python"]
CMD ["app.py"]
# docker run myimg → python app.py
# docker run myimg other.py → python other.py (still runs python!)

4 Layer-caching best practices

  • Order instructions from least to most frequently changing.
  • Combine related RUN commands with &&.
  • Use a .dockerignore to exclude node_modules, .git, logs.
  • Prefer slim/alpine base images.
# .dockerignore example

.git
*.log
