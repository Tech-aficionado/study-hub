❤️ Healthchecks & Restart Policies Intermediate

Teaching Docker the difference between "the process is alive" and "the app actually works" — and what to do when it isn't.

1 Why "running" isn't the same as "working"

A container can be perfectly "up" in docker ps while the app inside it is wedged — a web server stuck in an infinite loop, a process that started but can't reach its database, a thread pool that deadlocked. The process didn't crash, so Docker thinks everything is fine. It isn't.

A healthcheck closes that gap. Instead of trusting "the process exists", Docker periodically runs a command you choose inside the container and asks: can you still do your job? Think of it like a nurse taking a patient's pulse every few minutes rather than just checking they're lying in the bed.

💡 Liveness ("is the process there?") is what Docker tracks by default. A healthcheck adds readiness/health ("can it actually serve requests?") — the thing your users care about.

2 Writing a HEALTHCHECK

You add it in the Dockerfile. The command's exit code is the verdict: 0 means healthy, 1 means unhealthy (2 is reserved — don't use it).

# check every 30s that the site answers within 3s; 3 strikes = unhealthy
HEALTHCHECK --interval=30s --timeout=3s --retries=3 --start-period=10s \
  CMD curl -f http://localhost/ || exit 1
OptionDefaultMeaning
--interval30sTime between checks
--timeout30sA check slower than this counts as a failure (killed with SIGKILL)
--retries3Consecutive failures before the status flips to unhealthy
--start-period0sGrace window at startup — failures here don't count against retries
--start-interval5sFaster check cadence during the start period (needs Engine 25.0+)

The status moves starting → healthy on the first pass, and only flips to unhealthy after retries failures in a row. HEALTHCHECK NONE disables one inherited from a base image.

Check the result with docker ps (the STATUS column shows (healthy)) or docker inspect --format '{{.State.Health.Status}}' <name>. Any text the check writes to stdout/stderr is stored (first 4 KB) and visible in docker inspect — handy for debugging a failing probe.

3 Restart policies — self-healing containers

A restart policy tells the Docker daemon whether to bring a container back automatically when it exits or when Docker itself restarts. Set it with --restart.

PolicyWhat it does
noNever restart automatically. The default.
on-failure[:N]Restart only if it exits with a non-zero (error) code. Optional cap of N attempts. Does not restart on daemon restart.
alwaysAlways restart. Also starts on daemon restart. A manual stop keeps it down only until the daemon next restarts.
unless-stoppedLike always, but if you stopped it, it stays stopped even across daemon restarts.
docker run -d --restart unless-stopped --name redis redis

# change the policy on an existing container, no re-create needed
docker update --restart on-failure:5 web

# make every running container come back after a reboot
docker update --restart unless-stopped $(docker ps -q)
⚠️ A restart policy only takes effect after the container has run successfully for at least 10 seconds. That rule exists to stop a container that crashes instantly from spinning in a tight restart loop.

4 Putting them together, and a gotcha

Healthchecks and restart policies answer different questions. A restart policy reacts to the process exiting; a healthcheck detects a process that's alive but broken. On a single host, a plain --restart does not automatically restart a container just because it went unhealthy — that automatic reaction is an orchestrator feature (Swarm services, Kubernetes liveness probes). On one Docker host, the healthcheck is still valuable as a signal: docker ps shows it, Compose can gate depends_on on it, and you can watch for it.

# compose: don't start web until the DB is actually ready, not just started
services:
  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 5
  web:
    build: .
    depends_on:
      db:
        condition: service_healthy
🚫 Don't combine Docker restart policies with a host process manager (systemd starting the container and --restart always) — the two fight over the container and you get confusing double-restarts. Pick one.
